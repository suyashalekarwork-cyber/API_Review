Ventus — Unified Schema Field Reference

Scope: Every unified-schema column that Ventus actually populates in data_pipeline/unified_database/unified_products.csv (source = "Ventus"). Ventus supplies 20 of the 87 unified/companion columns across its 19 products (the smallest of all 7 sources); the rest are always blank for this source and are not documented here.

Audience: Team members looking up what a field means and where it comes from. This is NOT a data-quality report — for null rates and QA flags see reports/ventus_column_analysis.md instead.

Pipeline stages behind this doc (oldest → newest): 1. etl_ventus.py — reads data/Ventus/*.json (19 files, no root nesting key), flattens every nested key to dot-notation, writes the 21-column raw base to exports/ventus_etl_v1.csv. 2. scripts/build_ventus_stage1.py — reads exports/ventus_etl_v1.csv, adds 3 HTML-stripped *_clean companion columns (description_clean, terms.booking_terms_clean, terms.fit_to_fly_terms_clean); drops nothing, writes exports/ventus_stage1.csv (24 columns). 3. scripts/build_ventus_stage2.py — reads the Stage 1 CSV (data_pipeline/stage1/ventus_stage1.csv), renames/selects 16 columns to unified names via a fixed COLUMN_RENAME list, derives product_price from the pricing JSON list, writes data_pipeline/stage2/ventus_stage2.csv (17 columns: 16 renamed + product_price). 4. scripts/build_unified_database.py — folds Stage 2 into unified_products.csv; for Ventus this adds the source literal (Ventus has no source column of its own — needs_source_col=True), derives product_price_numeric (a straight float() cast since Ventus's product_price is already a scalar), and wraps product_category into a JSON-list string (["General Flight"]) since the raw value is a plain string, not a list.

Example product used throughout: product_id = 46 ("Yarra Valley Balloon Flight with Breakfast & Transfers", filename Ventus-2-46.json) — chosen because it's one of only 5/19 rows with real transfer data and one of only 7/19 rows with real description/cancellation text populated, so every documented field has a real, non-blank value.

Identity

product_id

  • Type: string (numeric-looking, e.g. "46")
  • Description: Ventus's product identifier.
  • How built: Filename only — there is no internal ID field anywhere in Ventus's JSON. Verified during ETL build: 0/19 raw files contain any scalar value matching the filename's product-ID segment at any nesting depth (the only internal id fields present are unrelated: flight_type.id, location.id, inclusions.non_flight_items[].non_flight_items_id.id). etl_ventus.py::parse_product_id_from_filename() takes everything after the first two hyphen-separated segments of Ventus-{supplierId}-{productId}.json (the same hyphen-safe rule used for CustomLinc) — written into column _filename_product_id, which Stage 2 renames straight to product_id. Because there's no internal ID to cross-check against, this value can never be verified against JSON content the way it can for other sources — the filename is trusted directly. Structural safety was verified instead: all 19 filenames have exactly 3 hyphen segments with no hyphens inside the product-ID segment itself, so this rule and a naive "last-segment" rule agree on every file.
  • Example: 46 (from Ventus-2-46.json)

source

  • Type: string (constant)
  • Description: Marks which of the 7 supplier systems this row came from.
  • How built: Ventus's Stage 2 CSV has no source column of its own; build_unified_database.py adds the hardcoded literal "Ventus" for every row (needs_source_col=True in the SOURCES list).
  • Example: Ventus

Listing Page Fields

product_name

  • Type: string
  • Description: Full tour/product name.
  • How built: Direct from raw field name.
  • Example: Yarra Valley Balloon Flight with Breakfast & Transfers (trailing space present in the raw source value, not a pipeline artifact)

product_price

  • Type: number (decimal, dollars)
  • Description: Starting price for the product.
  • How built: Not a dedicated API field — Ventus's raw pricing field is an 8-entry list per product (2 passenger types Adult/Child × 2 rate periods anyday/weekday × 2 rate kinds rate/sales_rate). Stage 2's derive_product_price() picks the single entry where attribute_name == "Adult" and rate_type == "anyday_sales_rate" — the discounted/current-offer adult rate, chosen over min() across all 8 entries because a bare minimum would surface the Child rate, which can mislead as a "starting price" since children typically must be accompanied by a paying adult. All 19/19 rows had a matching entry (no missing prices).
  • Example: 484.5

product_price_numeric

  • Type: number
  • Description: Companion numeric-price column added at the unified-database merge step so every source has one consistent numeric price field.
  • How built: For Ventus, product_price is already a scalar, so this is just float(product_price) cast straight through — no transformation. (build_unified_database.py::derive_price_numeric())
  • Example: 484.5

product_images

  • Type: JSON-list-as-string (always exactly 1 URL for Ventus)
  • Description: Gallery images.
  • How built: Direct from raw images list (already JSON-string at the ETL flatten step), passed through unchanged at Stage 2. Every one of the 19 products has exactly 1 image — no product has 0 or more than 1.
  • Example: ["https://ventus.globalballooning.com.au/app/assets/photos/YarraValley/YV-Sunrise.jpg"]

product_category

  • Type: JSON-list-as-string (always a single-item list for Ventus)
  • Description: Tour type.
  • How built: Direct from raw flight_type.name — Ventus has only one observed value across all 19 products ("General Flight"), so this field carries no real differentiation for this source today. Renamed at Stage 2 (COLUMN_RENAME); wrapped into a JSON-list string (["General Flight"]) at the unified-database step by normalize_category(), which wraps any plain-string category value into a single-item list for cross-source consistency (Ventus's raw value fails the json.loads() list-parse attempt, so it falls into the plain-string branch).
  • Example: ["General Flight"]

flight_type_id

  • Type: number
  • Description: Internal reference ID for product_category — not a named unified-schema field, kept as a stable key alongside the category name.
  • How built: Direct from raw flight_type.id. Only 1 unique value (1) across all 19 products, matching product_category's single observed value.
  • Example: 1

Location Fields

location_city

  • Type: string
  • Description: City/region for the product.
  • How built: Direct from raw location.name (e.g. "Yarra Valley", "Byron Bay", "Camden (Sydney)"). Note — this deviates from the CLAUDE.md Source Field Mapping table, which documents Ventus's location_name → location_street. The real Stage 2 build script (COLUMN_RENAME) maps location.name → location_city, not location_street — verified directly in code (build_ventus_stage2.py line 29). No location_street column exists anywhere in ventus_stage2.csv or unified_products.csv for Ventus. This is a real discrepancy between the schema-mapping doc and the actual pipeline, worth flagging to whoever owns the unified schema rather than silently treating the doc as correct.
  • Example: Yarra Valley

location_id

  • Type: number
  • Description: Internal reference ID for location_city — not a named unified-schema field, kept as a stable key alongside the location name.
  • How built: Direct from raw location.id. 7 unique values across 19 products (one per distinct region/venue).
  • Example: 3

Detail Page Fields

detail_description

  • Type: string (long text, HTML-stripped)
  • Description: "About the Experience" section.
  • How built: Raw field description is HTML (block-level <p>/<ul>/<li> tags back-to-back with no separating whitespace). Stage 1 (build_ventus_stage1.py::strip_html()) applies the project's standard HTML-cleaning pattern: inserts a space at each <p>/<ul>/<li> boundary via regex before stripping tags (so adjacent paragraphs/list-items don't get mashed together), strips all remaining tags, then decodes entities with stdlib html.unescape(). The cleaned result lands in description_clean, which Stage 2 renames straight to detail_description. Only 7/19 rows are populated — Ventus has no description at all for the other 12 products, not a data-loss artifact of cleaning. Content quirk worth flagging: despite the field name, the raw description value for every one of the 7 populated Ventus products is actually cancellation-policy text ("In the event of a flight cancellation, you may: Rebook within 12 months / Request a refund within 6 months..."), not a tour description — confirmed both in the unified CSV and by reading the raw source JSON directly for product 46. This looks like upstream mislabeling in Ventus's own API rather than anything introduced by the ETL/Stage pipeline; detail_description for Ventus should not be assumed to describe the experience the way it does for other sources.
  • Example: In the event of a flight cancellation, you may: Rebook within 12 months Request a refund within 6 months of the cancellation date.

detail_cancellation_policy

  • Type: string (long text, HTML-stripped)
  • Description: Cancellation Policy section.
  • How built: Same HTML-cleaning pattern as detail_description, applied to raw field terms.booking_terms → Stage 1's terms.booking_terms_clean → renamed to detail_cancellation_policy at Stage 2. Only 7/19 rows populated — same 37% fill rate as detail_description, since both are sourced from the same sparse terms/description blocks in the raw API (a product with one tends to have the other).
  • Example: Upon purchasing this flight or gift voucher, you are agreeing to the Global Ballooning Terms & Conditions, as stipulated on our website - https://www.globalballooning.com.au/terms-conditions/ Important key points: Changes to bookings: Changes made between 7 days and 48 hours before your flight incur a $50 per person fee. Within 48 hours: No changes or cancellations are permitted within 48 hours of your scheduled flight...

detail_health_safety

  • Type: string (long text, HTML-stripped)
  • Description: Health & Safety section.
  • How built: Same HTML-cleaning pattern, applied to raw field terms.fit_to_fly_terms → Stage 1's terms.fit_to_fly_terms_clean → renamed to detail_health_safety at Stage 2. 19/19 rows populated (100% fill rate) — every Ventus product has fitness-to-fly terms, unlike detail_description/detail_cancellation_policy.
  • Example: Hot Air Ballooning is an outdoor adventure activity that involves some active participation from passengers and as such a minimum level of fitness and well-being is required. By noting your agreement and completing this booking, you will notify us if members of your booking party have: significant knee, hip, back or neck problems...

has_breakfast_included / breakfast_details

  • Type: has_breakfast_included = boolean; breakfast_details = string
  • Description: Companions supporting the "What's Included" section — not named unified-schema fields themselves (Ventus has no dedicated detail_what_is_included mapping), but kept as real inclusion content.
  • How built: Direct from raw inclusions.has_pax_breakfast (100% filled boolean) and inclusions.breakfast_name (79%, 15/19 filled — populated whenever has_pax_breakfast is true).
  • Example: has_breakfast_included = True, breakfast_details = "Buffet Breakfast"

has_transfer_included / transfer_id / transfer_name / transfer_pickup_hotels

  • Type: has_transfer_included = boolean; transfer_id = number; transfer_name = string; transfer_pickup_hotels = JSON-list-as-string
  • Description: Companions supporting pickup/Meeting Point information — not named unified-schema fields themselves.
  • How built: has_transfer_included direct from raw inclusions.has_pax_transfer (100% filled boolean). transfer_id / transfer_name / transfer_pickup_hotels come from raw inclusions.transfer.id / .name / .attributes — only 5/19 rows populated (whenever a transfer actually exists; has_pax_transfer is the reliable indicator of whether a transfer exists, these three carry the detail when it does). transfer_pickup_hotels is a list of {"attributes_id": {"name","phone","address","id"}} pickup-hotel objects and varies enormously in length across the 5 populated rows (1 to 77 items) — kept as a single JSON-string column per the project's list-field pattern rather than exploded into separate rows/columns. Note: the sibling raw column inclusions.transfer (no suffix) is a 100%-empty flattening artifact — whenever the underlying transfer object is populated, the flattener expands it into the .id/.name/.attributes columns instead, leaving the bare parent key always blank. It is not selected into Stage 2 for this reason.
  • Example: has_transfer_included = True, transfer_id = 24, transfer_name = "Return Transfer � pick up from Pullman East Melbourne (192 Wellington Parade, Melbourne)" (the � is U+FFFD, present in the raw source JSON itself — verified by reading data/Ventus/Ventus-2-46.json directly; an unrecoverable upstream encoding loss, not a pipeline bug — see CLAUDE.md's mojibake note), transfer_pickup_hotels = [{"attributes_id": {"phone": "(03) 9419 2000", "address": "192 Wellington Parade, East Melbourne VIC 3002", "id": 235, "name": "Pullman East Melbourne - 192 Wellington Parade, East Melbourne (Drop off: Pullman East Melbourne)"}}]

non_flight_inclusions

  • Type: JSON-list-as-string
  • Description: Extra inclusions beyond the flight itself (e.g. souvenirs, photos) — not a named unified-schema field, supports the "What's Included" section alongside the breakfast/transfer companions above.
  • How built: Direct from raw inclusions.non_flight_items, a list of {"non_flight_items_id": {"id","name"}, "pax": bool} objects. 100% filled (19/19); 7/19 rows have more than one item.
  • Example: [{"pax": true, "non_flight_items_id": {"name": "Complimentary In-Flight GoPro Photos ", "id": 25}}, {"pax": true, "non_flight_items_id": {"name": "Digital Flight Certificates", "id": 26}}, {"pax": false, "non_flight_items_id": {"name": "Luxe Balloon Magnet", "id": 39}}]

Fields Ventus Does NOT Populate

Per the unified schema table and Source Field Mapping table in CLAUDE.md, Ventus is documented as a source for: - detail_what_is_included (from inclusions_non_flight_items) — the raw content exists (non_flight_inclusions, has_breakfast_included, breakfast_details) but was not renamed to the unified field name detail_what_is_included in Stage 2's COLUMN_RENAME list; these columns are carried into unified_products.csv only under their Ventus-specific names, not the shared unified name. A cross-source aggregator looking specifically for detail_what_is_included will find Ventus rows blank despite Ventus having real inclusion data. - location_street (documented as location_name → location_street) — the real code maps location.name to location_city, not location_street (see that field's note above). No location_street column exists for Ventus at all. - product_duration, product_currency, detail_languages — CLAUDE.md's unified-schema summary tables imply broader per-source coverage in places, but Ventus's raw JSON has no duration field, no explicit currency field, and no language field; these were correctly never selected because the source data doesn't exist, not a Stage 2 omission.

Fields Documented But Not Selected for the Unified Schema

These raw/Stage 1 columns exist in ventus_stage1.csv but were deliberately excluded from ventus_stage2.csv, so they never reach unified_products.csv:

  • valid — an internal product-active/validity boolean, not customer-facing content.
  • inclusions.transfer — 100% empty flattening artifact (see has_transfer_included/transfer_id note above); the real data lives in the sibling .id/.name/.attributes columns instead.
  • _source_filename — ETL bookkeeping (original JSON filename), not product data.
  • description (raw) / terms.booking_terms (raw) / terms.fit_to_fly_terms (raw) — superseded by their _clean HTML-stripped companions, which are what Stage 2 actually selects (description_clean → detail_description, terms.booking_terms_clean → detail_cancellation_policy, terms.fit_to_fly_terms_clean → detail_health_safety).
  • pricing (raw 8-entry rate list) — not carried into Stage 2 as its own column; only the derived single-value product_price (Adult anyday_sales_rate) survives. The full rate table (Adult/Child × anyday/weekday × rate/sales_rate) is available in ventus_stage1.csv if a future portal feature needs more than one price point.
