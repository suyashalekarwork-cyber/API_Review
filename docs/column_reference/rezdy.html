Rezdy — Unified Schema Field Reference

Scope: Every unified-schema column that Rezdy actually populates in data_pipeline/unified_database/unified_products.csv (source = "Rezdy"). Rezdy supplies 33 of the 87 unified columns; the rest are always blank for this source and are not documented here.

Audience: Team members looking up what a field means and where it comes from. This is NOT a data-quality report — for null rates, outliers, and QA flags see reports/column_reference/rezdy_master_column_reference.md (Stage 1 profile) instead.

Pipeline stages behind this doc (oldest → newest): 1. scripts/build_rezdy_master.py — combines raw JSON from data/Rezdy/*.json (root key product, 9,373 files) with 6 OpenAI Batch API .jsonl output files (LLM extraction over each product's raw description text), writing the 47-column data_pipeline/stage1/rezdy_master.csv (9,363 rows). 2. scripts/build_rezdy_stage2.py — selects/renames 31 Stage 1 columns to unified names and performs 1 real field merge (detail_cancellation_policy), writing data_pipeline/stage2/rezdy_stage2.csv (32 columns). 3. scripts/build_unified_database.py — folds Stage 2 into unified_products.csv; for Rezdy this uppercases product_currency, normalizes location_country to a 2-letter code where recognized, and derives product_price_numeric (for Rezdy this is just float(product_price) passed straight through — no unwrapping needed, unlike Livn). Rezdy already carries its own literal source column from Stage 1, so build_unified_database.py's needs_source_col=False flag means this step does not overwrite or add one for Rezdy.

Note on the AI-extraction pipeline: every detail_* field below (plus detail_cancellation_policy's fallback half) is populated by an LLM extraction pass over each product's raw product.description text — the same 6-batch OpenAI Batch API pipeline documented in reports/rezdy_manager_report.md. It is not read directly off a structured Rezdy API field the way, say, location_city is. Where a field also has a genuine dedicated raw-API counterpart (only detail_cancellation_policy qualifies here, via direct_terms = raw product.terms), that's called out explicitly below per CLAUDE.md Critical Rule #10.

Example product used throughout: product_id = PZDTWJ ("Kakadu National Park - Sunset / Evening Tour ... Departing Darwin", supplier alias sacredowltours) — chosen because it has real, non-empty values in every rich detail/location field, so the merge and extraction behavior is visible.

Identity

product_id

  • Type: string (Rezdy product code, e.g. "PZDTWJ")
  • Description: Rezdy's unique product identifier.
  • How built: From the batch LLM output's custom_id prefix (split on "|"), cross-checked against raw JSON product.productCode/productId during the Stage 1 join. NOT the filename — though for the ~10 dead API-error stub files with no payload, build_rezdy_master.py falls back to the filename's last hyphen-segment (data/Rezdy/Rezdy-{supplierAlias}-{productId}.json).
  • Example: PZDTWJ

source

  • Type: string (constant)
  • Description: Marks which of the 7 supplier systems this row came from.
  • How built: Hardcoded literal "Rezdy", assigned in build_rezdy_master.py's row-building loop and carried through unchanged at every later stage (Rezdy is one of only two sources — with Fareharbor — that already has its own source column before the unified-database merge step, so build_unified_database.py does not add or overwrite it here).
  • Example: Rezdy

supplier_alias

  • Type: string
  • Description: URL/filename-safe slug for the supplier — the same value that appears in data/Rezdy/Rezdy-{supplierAlias}-{productId}.json filenames (which can themselves contain hyphens).
  • How built: Direct from raw JSON product.supplierAlias.
  • Example: sacredowltours

Listing Page Fields

product_name

  • Type: string
  • Description: Full tour/product name.
  • How built: Direct from raw field product.name.
  • Example: Kakadu National Park - Sunset / Evening Tour - Featuring the Multi- Award Winning Yellow Water River Cruise at Sunset - 1 Day Tour - Departing Darwin

product_headline

  • Type: string
  • Description: Short tagline shown under the product name (though at ~169 chars average across Rezdy overall, it reads more like a marketing blurb than a true one-liner).
  • How built: Direct from raw field product.shortDescription.
  • Example: Experience the breathtaking beauty of Kakadu with a Sunset Cruise on Yellow Water River, followed by a delicious dinner, a visit the Warradjan Cultural Centre and Njourlangie Rock Art for a deeper und...

product_price

  • Type: number (string-formatted decimal, dollars)
  • Description: Starting/advertised price for the product.
  • How built: Direct from raw field product.advertisedPrice.
  • Example: 599.0

product_price_numeric

  • Type: number
  • Description: Companion numeric-price column added at the unified-database merge step so every source has one consistent numeric price field (needed because Livn's product_price is a JSON object, not a scalar).
  • How built: For Rezdy, product_price is already a scalar, so derive_price_numeric() in build_unified_database.py just does float(product_price) and passes the value straight through — no transformation, unlike the Livn {amount: ...} unwrap.
  • Example: 599.0

product_currency

  • Type: string (ISO code)
  • Description: Currency the price is quoted in.
  • How built: Direct from raw field product.currency (Rezdy has a genuine dedicated currency field, unlike Fareharbor which has to infer it from tax rate), defaulting to "AUD" when absent. Uppercased at the unified-database merge step (normalize_currency()), though Rezdy's raw values are already consistently uppercase in practice.
  • Example: AUD

price_options

  • Type: string (pipe-joined list)
  • Description: Human-readable breakdown of fare tiers and their prices, supporting product_price — no dedicated unified field name exists for this yet, but it was selected into Stage 2/the unified DB as useful supporting pricing data.
  • How built: Computed by build_price_options() in build_rezdy_master.py from raw product.priceOptions — takes the first 5 options, joins each "{label}: ${price}" pair with " | ".
  • Example: Adult: $599.0 | Child: $550.0

product_duration / duration_display

  • Type: product_duration = number (minutes); duration_display = string (human-readable)
  • Description: How long the tour runs.
  • How built: product_duration direct from raw product.durationMinutes. duration_display is computed from that same value via build_duration(): >=1440 min → "N days", >=60 min → "N hrs" (one decimal if not whole), else "N mins"; returns "" for mins <= 0, which is why duration_display has slightly more nulls than product_duration across the dataset.
  • Example: product_duration = 720, duration_display = "12 hrs"

product_main_image / product_images / image_count

  • Type: product_main_image = single URL string; product_images = pipe-joined list of URL strings (capped at 10); image_count = integer
  • Description: Cover image and gallery images. Note: the unified schema table in CLAUDE.md documents product_main_image as "Fareharbor only" — this is stale; Rezdy clearly populates a real single-cover-image field too.
  • How built: product_main_image computed via get_main_image() — takes product.images[0] and resolves largeSizeUrl (falling back to thumbnailUrl, then itemUrl). product_images computed via get_all_images() — same per-image resolution, but across the full product.images list, capped at 10 URLs, joined with " | ". image_count is len(product.images) — this counts all images from the API, so it can legitimately exceed the 10 URLs actually listed in product_images (e.g. a product with image_count: 267 still only shows 10 URLs in the gallery string).
  • Example: product_main_image = "https://img.rezdy.com/PRODUCT_IMAGE/256901/e0026d_15e2d3ac34e04a4fa07dd7c3496ee717_mv2_lg.jpg", image_count = 22

Location Fields (Details API only, per Critical Rule #8)

location_street, location_city, location_state, location_country, location_postcode

  • Type: string
  • Description: Structured street address components. location_state is documented in the unified schema as "Rezdy only."
  • How built: Direct from raw product.locationAddress.{addressLine,city,state,countryCode,postCode} via get_nested(). location_country is normalized at the unified-database merge step (normalize_country()): already-2-letter values are uppercased as-is; recognized full names (e.g. "Australia") map to their ISO-2 code via a small lookup table; anything else (values like "NF", or unrecognized spellings) passes through unchanged. location_state is not normalized anywhere in the pipeline — Rezdy Stage 1 profiling found 177 distinct values against ~8 expected AU/NZ states, including at least one city name entered as a state ("Rotorua"), and that noise reaches the unified CSV as-is.
  • Example: location_street = "6 Bennett Street", location_city = "Darwin", location_state = "nt" (lowercase, unnormalized), location_country = "AU", location_postcode = "0800"

location_latitude / location_longitude

  • Type: number
  • Description: GPS coordinates.
  • How built: Direct from raw product.locationAddress.latitude / .longitude via get_nested().
  • Example: -12.4652392, 130.8432756

Detail Page Fields

All fields in this section except detail_cancellation_policy's primary half are LLM-extracted — see the pipeline-stages note above. The extraction pulls from 9 named JSON keys (about, highlights, what_is_included, what_is_not_included, itinerary, booking_notes, what_to_bring, cancellation_policy, other) in each batch response, parsed per-product by parse_batch_output()/parse_response() in build_rezdy_master.py.

detail_description

  • Type: string (long text)
  • Description: "About the Experience" section.
  • How built: LLM-extracted about key from the batch output (Stage 1 column desc_about), renamed straight through at Stage 2 — no merge with a raw description field.

  • How built: LLM-extracted highlights key (Stage 1 desc_highlights), passed straight through at Stage 2.
  • Example: "Yellow Water River Cruise : A spectacular 2-hour sunset cruise where you'll witness breathtaking views, birds in flight, and crocodiles gliding across the water. Aboriginal Rock Art Site : Explore anc..."

detail_what_is_included

  • Type: string (long text)
  • Description: "What's Included" section.
  • How built: LLM-extracted what_is_included key (Stage 1 desc_what_included), passed straight through at Stage 2.
  • Example: "Return Door-to-Door Transfers from Darwin, Experienced Tour Guide, Yellow Water River Cruise - 2 Hour Sunset Cruise, Aboriginal Rock Art Site, Wetlands Bird Hide, Cultural Centre Visit, Lunch at the T..."

detail_what_is_not_included

  • Type: string (long text)
  • Description: "What's Not Included" section. Unified schema table currently lists this as "Fareharbor only" — stale; Rezdy should be added.
  • How built: LLM-extracted what_is_not_included key (Stage 1 desc_what_excluded), passed straight through at Stage 2.
  • Example: "Travel insurance is highly recommended."

detail_itinerary

  • Type: string (long text)
  • Description: Cruise Route / Itinerary section — the sparsest detail field for Rezdy (populated for only 11.5% of rows dataset-wide), since most single-activity products have nothing to itemize.
  • How built: LLM-extracted itinerary key (Stage 1 desc_itinerary), passed straight through at Stage 2.
  • Example: "Our adventure begins at 10:30am, its a 3 hour drive through the lush landscapes of Kakadu National Park, your expert guide will offer fascinating insights into the natural and cultural wonders you're ..."

detail_booking_notes

  • Type: string (long text)
  • Description: Important Information section.
  • How built: LLM-extracted booking_notes key (Stage 1 desc_booking_notes), passed straight through at Stage 2. Note: Rezdy also has a dedicated raw field for similar content (product.additionalInformation), but that field was never captured as its own Stage 1 column — only this LLM-parsed rendition exists in the pipeline, so unlike detail_cancellation_policy there is no raw/parsed merge here despite CLAUDE.md's source-mapping table listing product.additionalInformation as the source.
  • Example: "Low levels of fitness required 1 km walk on tour (*optional walks on tour call for a medium level of fitness, there are optional)."

detail_what_to_bring

  • Type: string (long text)
  • Description: What To Bring section. Unified schema table currently lists this as "Fareharbor only" — stale; Rezdy should be added.
  • How built: LLM-extracted what_to_bring key (Stage 1 desc_what_to_bring), passed straight through at Stage 2.
  • Example: "- 1 to 1.5L re-fillable water bottle - Camera, Hat, Sunglasses - Insect Repellent & Sunscreen - Travel pillow to rest on the way to and from Kakadu. - Guests are required to bring their own medication..."

detail_accessibility

  • Type: string (pipe-joined list)
  • Description: Accessibility-related suitability tags. Unified schema table currently lists this as "Fareharbor only" — Rezdy has real data here too, though it's a rougher fit: this is not free-text like Fareharbor's structured_description.accessibility, it's a set of controlled tag values.
  • How built: Not LLM-extracted — this is the one detail field sourced from Rezdy's product.tags array instead of the batch pipeline. Rezdy's tags are flat "PREFIX:value" strings, not {name: ...} dicts (a documented CLAUDE.md quirk — calling .get('name') on them would silently fail). get_tag(p, "ACCESSIBILITY") in build_rezdy_master.py filters for entries starting "ACCESSIBILITY:", strips the prefix, and joins matches with " | " (Stage 1 column tag_accessibility), renamed straight through at Stage 2. The unified schema's product_tags field is separate and is not populated for Rezdy (see "Fields Rezdy Does NOT Populate" below) — only this one filtered tag category made it into the unified schema.
  • Example: "Vision Impaired | Hearing Impaired | Paraplegic | Asthmatic | Quadriplegic | Epileptic"

detail_cancellation_policy

  • Type: string (long text, pipe-joined when both sources have content)
  • Description: Cancellation Policy section.
  • How built: The one genuine 2-source merge in the Rezdy pipeline, per CLAUDE.md Critical Rule #10 (dedicated field wins, parsed fallback second): build_cancellation_policy() in build_rezdy_stage2.py takes direct_terms (raw product.terms, HTML-cleaned — the dedicated API field) as primary and desc_cancellation (LLM-extracted cancellation_policy key — the fallback) as secondary. If both are non-empty, they're joined with " | "; if only one is present, that one is used alone; if neither, the field is blank. Caveat: unlike Fareharbor's merged fields, there is no *_source provenance column tracking which source won for a given row (flagged as an open item in reports/rezdy_stage2_column_selection.md) — this is a gap against Critical Rule #10's "track which one won in a *_source column" requirement.
  • Example: "72 Hours notice is required for cancellations or amendments. | A strict cancellation policy applies, we require at least 72 hours' notice for a 100% refund. All cancellations under 72 hours will be a..." — this example shows both sources populated (the | join is visible mid-string).
  • Merge stats (9,363 rows total, from the real build_rezdy_stage2.py run): both sources populated → 386 rows (joined with |); direct_terms only → 2,991; desc_cancellation only → 585; neither → 5,401.

cancellation_days

  • Type: number
  • Description: Structured numeric companion to detail_cancellation_policy — the number of days before departure the policy's cutoff applies. Not a named unified-schema field itself, kept for portal logic that needs a cutoff without parsing free text. Caveat: a sentinel value of 9999 appears in the raw data (Rezdy Stage 1 profiling) as a placeholder, not a real day count — filter it out before any numeric use.
  • How built: Direct from raw field product.cancellationPolicyDays — despite the generic-sounding name, this is a genuine dedicated API field, not pipeline metadata.
  • Example: 7

Meta Fields (internal, not shown to customers)

meta_supplier_id

  • Type: integer
  • Description: Supplier's numeric account ID within Rezdy.
  • How built: Direct from raw product.supplierId.
  • Example: 256901

meta_supplier_name

  • Type: string
  • Description: Tour operator/supplier company name.
  • How built: Direct from raw product.supplierName.
  • Example: Sacred Owl Tours

Fields Rezdy Does NOT Populate

Per the unified schema table in CLAUDE.md, Rezdy is documented as a source for several fields that are not actually present in rezdy_stage2.csv, so they never reach unified_products.csv for this source:

  • product_tags — CLAUDE.md's LISTING PAGE table lists product_tags as available from "Rezdy, FH, TDU, Ingresso." Rezdy's raw product.tags array is real and populated, but it was only ever partially mined — build_rezdy_master.py splits it into 6 category-filtered columns (tag_accessibility, tag_age, tag_intensity, tag_interest, tag_skill, tag_suitability), and only tag_accessibility (as detail_accessibility) made it to Stage 2. There is no unfiltered product_tags equivalent for Rezdy in the unified schema at all — a genuine gap.
  • detail_health_safety, detail_min_age, detail_max_age, detail_group_size, detail_operating_days, detail_start_time, detail_languages — documented in CLAUDE.md's Source Field Mapping table as product.languages (for detail_languages) or simply absent for Rezdy on the others; none of these were ever captured as Stage 1 columns, so there's nothing to select at Stage 2.
  • detail_tax_percentage, is_pickup_available — Fareharbor-sourced concepts (item.tax_percentage, item.is_pickup_ever_available) with no Rezdy equivalent captured in the pipeline.

This is a gap between the schema-design doc and the actual Stage 1/2 build — worth flagging to whoever owns the unified schema, not something to silently work around in this reference doc.

Fields Documented But Not Selected for the Unified Schema

These raw/Stage-1 columns exist in rezdy_master.csv but were deliberately excluded from rezdy_stage2.csv, so they never reach unified_products.csv. Listed here so a reader who finds them in an earlier pipeline stage doesn't wonder where they went (see reports/rezdy_stage2_column_selection.md for the full selection rationale):

  • compound_key — regenerable (product_id|source), not carried into Stage 2.
  • batch_number, sections_filled, parse_success, truncated, word_coverage_pct, needs_retry — internal LLM-batch-pipeline QA metadata (which of the 6 batches processed the row, extraction success/truncation flags, word-coverage ratio, retry flag), not customer-facing.
  • product_type — Rezdy's own classification (ACTIVITY/DAYTOUR/MULTIDAYTOUR/TRANSFER/RENTAL/CUSTOM/etc., 13 values). CLAUDE.md explicitly notes "Rezdy uses product_type NOT category" — the unified schema's product_category field is documented as available from FH/CustomLinc/Ventus/Ingresso only, so product_type has no home in the 87-column unified schema and was left out of Stage 2 (confirmed: product_category is blank for every Rezdy row in unified_products.csv).
  • tag_age, tag_intensity, tag_interest, tag_skill, tag_suitability — the other 5 category-filtered slices of product.tags (only tag_accessibility was selected, as detail_accessibility). Real, populated data (roughly 3,900–4,100 of 9,363 rows each) left as UNCERTAIN in the Stage 2 selection report — no dedicated unified field name exists for age/intensity/interest/skill/suitability filtering yet.
  • desc_other — LLM-extracted catch-all bucket (other key) for content that didn't fit any of the other 8 named sections. Left as UNCERTAIN rather than excluded outright — flagged as possibly containing real usable content (accessibility notes, extra terms) worth a manual read before a future schema decision.
