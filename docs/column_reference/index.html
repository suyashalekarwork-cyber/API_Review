Column Reference Documentation

This folder contains unified-schema field reference documentation for each supplier source in the TDU B2B Travel Portal data pipeline.

Each file documents every unified-schema column that source actually populates in data_pipeline/unified_database/unified_products.csv / .db: - What the field means (plain English) - Data type - How it was built — traced back to the real raw API field, ETL/Stage 1/ Stage 2 build script, and any merge/fallback logic actually used in code - One real example value (with product_id) pulled from live data

This is reference documentation, not a data-quality audit — for null rates, outliers, and QA flags, see the HTML data-quality dashboard and the per-source reports/{source}_column_analysis.md files instead.

TDU — Not Yet Documented (Pipeline Gap, Not Just a Docs Gap)

TDU (2,367 products) has no ETL/Stage 1/Stage 2 build script and is not present in unified_products.csv/.db at all — the unified database currently merges only the 6 sources listed above. A reference doc can't meaningfully describe unified-schema fields for data that was never merged in, so none was written.

Building etl_tdu.py → Stage 1 → Stage 2 (mirroring the other 6 sources) is real pipeline work, not documentation, and needs its own scoping before a TDU reference doc can follow the same format as the rest of this folder.

Naming Convention

Unified-schema docs follow the pattern: {source}_reference.md (lowercase source name, e.g. rezdy_reference.md).

The superseded Stage 1 docs follow the older pattern: {stage1_master_filename}_column_reference.md.

Notes

  • Every unified-schema doc traces each field's "how built" note back to the actual Stage 1/Stage 2 build script in scripts/, not to the earlier reports/{source}_stage2_column_selection.md proposal reports — several real discrepancies between the proposed and actual merge logic were found and corrected in the process (e.g. Fareharbor's detail_highlights uses only the AI-extracted value in the real build, not a structured-preferred/ AI-fallback merge as an earlier report proposed).
  • Each doc also documents fields the unified schema table in CLAUDE.md claims a source provides but that are actually absent from unified_products.csv for that source (e.g. Fareharbor is missing detail_accessibility/detail_min_age/detail_max_age/ detail_group_size/ratings; Ventus's location_name maps to location_city in real code, not location_street as CLAUDE.md's mapping table states) — these are genuine schema-vs-build mismatches worth fixing at the source, not documentation errors to silently paper over.
