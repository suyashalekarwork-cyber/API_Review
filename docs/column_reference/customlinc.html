Column Reference / CustomLinc

CustomLinc — Unified Schema Field Reference

  • Scope: Every unified-schema column that CustomLinc actually populates in data_pipeline/unified_database/unified_products.csv (source = "CustomLinc"). CustomLinc supplies 29 of the 87 unified columns (30 including the source column itself); the rest are always blank for this source and are not documented here. CustomLinc is the smallest source by far — 24 products total — and has no description field of any kind in its Details API, making it the weakest source per CLAUDE.md's source quality table.
  • Audience: Team members looking up what a field means and where it comes from. This is NOT a data-quality report — for null rates, outliers, and QA flags see reports/customlinc_column_analysis.md instead.

Pipeline stages behind this doc

etl_customlinc.py

reads data/CustomLinc/*.json (24 files, flat root object, no nesting key like Rezdy/TDU's product or Fareharbor's item), writes the 62-column raw ETL base to exports/customlinc_etl_v1.csv. Zero cleaning/dropping. Also derives _filename_product_id and _source_filename.

scripts/build_customlinc_stage1.py

reads exports/customlinc_etl_v1.csv, keeps every original column untouched, adds 8 _clean/derived companion columns (never overwrites an original), writes exports/customlinc_stage1.csv (70 columns, 24 rows). Note: a second, identically-named copy also exists at data_pipeline/stage1/customlinc_stage1.csv — Stage 2 (below) reads from the data_pipeline/stage1/ path, not the exports/ one the script's own header comment describes; both were verified to have the same 70 columns for this reference.

scripts/build_customlinc_stage2.py

renames/selects 27 columns to unified/output names, derives 2 new ones (product_price, departure_date), writes data_pipeline/stage2/customlinc_stage2.csv (29 columns, 24 rows).

scripts/build_unified_database.py

folds Stage 2 into unified_products.csv. For CustomLinc this adds the literal source column (CustomLinc doesn't carry one itself, per SOURCES list entry ("CustomLinc", ..., True)), normalizes product_currency (uppercase), and normalizes product_category into a JSON string list — CustomLinc's raw productTypeCode is a plain string (e.g. "TOUR"), so normalize_category() wraps it as ["TOUR"] since it isn't valid JSON to begin with. Also derives product_price_numeric (a straight float() cast — CustomLinc's product_price is already a scalar, no unwrapping needed, unlike Livn).

  • Example product used throughout: product_id = SK1130QR4PUC ("Skyrail Train with hotel pick up Cairns", source file CustomLinc-skyrail-SK1130QR4PUC.json) — chosen because it's one of only 2 of the 24 CustomLinc products with location_street populated, and also has package_groups/pickup_locations_general populated, so it shows the most fields with real, non-empty values.

Identity

product_id

  • Type: string
  • Description: CustomLinc's unique product identifier.
  • How built: From Stage 1's _filename_product_id, itself derived in etl_customlinc.py::parse_product_id_from_filename() as everything after the first two hyphen-separated segments of the filename (CustomLinc-{supplierAlias}-{productId}.json), joined back with -. This is the correct-by-construction fix for the fact that CustomLinc's own internal ID field (code) itself frequently contains hyphens (e.g. RFF-DR-GIT) — a naive "last hyphen segment" rule would truncate it to just GIT. Verified against the actual Stage 1 CSV: _filename_product_id agrees with raw code on all 24/24 rows, including RFF-DR-GIT.
  • Example: SK1130QR4PUC

source

  • Type: string (constant)
  • Description: Marks which of the 7 supplier systems this row came from.
  • How built: CustomLinc's Stage 2 CSV has no source column of its own; build_unified_database.py adds the hardcoded literal "CustomLinc" at merge time (SOURCES list, needs_source_col=True).
  • Example: CustomLinc

Listing Page Fields

product_name

  • Type: string
  • Description: Full tour/product name.
  • How built: From Stage 1's name_clean, not raw name — the Stage 1 cleaning step (collapse_whitespace()) collapses repeated internal whitespace (a double-space bug present in some product names) but does not strip/trim.
  • Example: Skyrail Train with hotel pick up Cairns

product_category

  • Type: string (JSON-encoded list, one element)
  • Description: Tour type/category.
  • How built: Direct from raw productTypeCode (controlled vocabulary: ENTRY or TOUR across all 24 rows), renamed straight through at Stage 2. At the unified-database merge step, normalize_category() wraps it in a JSON list — CustomLinc's raw value is a plain string, not valid JSON, so it falls into the except branch and becomes json.dumps([raw]).
  • Example: ["TOUR"]

product_type_flag

  • Type: string (short code)
  • Description: Not a named unified-schema field — a supporting classifier kept alongside product_category.
  • How built: Direct from raw isA (observed values: CT, PK, PR, PS).
  • Example: PS

product_currency

  • Type: string (ISO code)
  • Description: Currency the price is quoted in.
  • How built: Direct from raw currency (100% AUD across all 24 rows), uppercased at the unified-database merge step (no-op here since it's already uppercase).
  • Example: AUD

product_price

  • Type: number
  • Description: Starting price for the product.
  • How built: Not the raw lowestPrice column, despite the name suggesting it — lowestPrice is 0 for all 24 rows in both the Stage 1 CSV and the raw source JSON (confirmed dead/unused field, per the Stage 2 script's own header comment). Instead, derive_product_price() in build_customlinc_stage2.py computes the minimum priceGross across all fare-tier entries in the raw fareTypes list, excluding entries where priceGross == 0 (this excludes genuinely-free/inapplicable tiers like Infant, which would otherwise always win the minimum). If no fare tier has a positive priceGross, the field is left blank.
  • Example: 66 — for SK1130QR4PUC, fareTypes has 4 tiers (Adult $132, Child $66, Infant $0, Family $330); Infant's $0 is excluded, so the minimum of the remaining three (66) wins.

product_price_numeric

  • Type: number
  • Description: Companion numeric-price column added at the unified-database merge step so every source has one consistent numeric price field (needed because Livn's product_price is a JSON object, not a scalar).
  • How built: For CustomLinc, product_price is already a scalar number, so derive_price_numeric() just does float(product_price) straight through — no unwrapping.
  • Example: 66

product_duration

  • Type: number (minutes)
  • Description: How long the tour runs.
  • How built: From Stage 1's duration_minutes, not raw duration — parse_duration() in build_customlinc_stage1.py standardizes two observed raw formats into total minutes: plain day-counts (raw duration like "1", interpreted per durationLong's "N Day(s)" wording as days * 24 * 60) and HH:MM clock durations (raw duration like "02:00", interpreted as hours*60 + minutes).
  • Example: 1440 (i.e. "1" raw day-count → 1 × 24 × 60)

duration_unit_source

  • Type: string ("days" / "HH:MM" / "unrecognized")
  • Description: Not a named unified-schema field — tracks which of the two raw duration formats product_duration was actually parsed from, per CLAUDE.md Critical Rule #10's "track which source won" pattern.
  • How built: Set alongside duration_minutes in the same parse_duration() function.
  • Example: days

duration_display

  • Type: string
  • Description: Human-readable duration string — display companion to product_duration.
  • How built: Direct from raw durationLong (e.g. "1 Day", "02:00 Hrs").
  • Example: 1 Day

Location Fields (Details API only, per Critical Rule #8)

location_street

  • Type: string
  • Description: Street address / meeting point — the only location field CustomLinc populates (per CLAUDE.md's Source Field Mapping table, startLocation → location_street is CustomLinc's sole documented location mapping; no city/state/country/postcode/lat/long fields exist for this source at all).
  • How built: Direct from raw startLocation, renamed straight through. Extremely sparse: only 2 of 24 rows populated (both are the two Skyrail products, both = "Skyrail Smithfield Terminal"). A duplicate raw column, endLocation, carries the identical value on the same 2 rows wherever either is populated — it was not selected into the unified schema since it's not a distinct data point, just a repeat of startLocation.
  • Example: Skyrail Smithfield Terminal

Detail Page Fields

detail_operating_days

  • Type: string
  • Description: Schedule section (CustomLinc/Livn per the unified schema table).
  • How built: Direct from raw operatingDays, renamed straight through. Only 4 of 24 rows populated (BIT1115, BIT1345, GIT1130, RFF-DR-GIT), all with the single observed value "Daily".
  • Example (product GIT1130): Daily — blank on the example product SK1130QR4PUC used elsewhere in this doc.

detail_start_time

  • Type: string — currently always blank for CustomLinc
  • Description: Departure Time section (documented CustomLinc/Livn source per the unified schema table).
  • How built: Mapped from Stage 1's departureTime_clean, which is itself Stage 1's null-out fix for raw departureTime — every one of the 24 raw departureTime values is a pre-1900 .NET placeholder epoch (/Date(-62135...)/, year ≈ 0001), which build_customlinc_stage1.py::clean_epoch_date() treats as "no real date set" and blanks out. So the unified column exists and the mapping is real, but there is currently zero populated data for this field across all 24 CustomLinc rows in unified_products.csv — confirmed 0/24. A separate raw field, departing (mapped to departure_time_display below), does carry a real (if generic) time value and may be a better field to surface in a UI needing something for departure time.
  • Example: (no populated example exists in the current 24-row dataset)

Fields With No Unified-Schema Name (kept as useful supporting data)

CustomLinc's Stage 2 output includes 16 columns that don't map to one of the 43 named unified fields but were kept because they carry real, non-trivial data useful to the portal or to booking-flow logic. Listed here since they do appear in unified_products.csv for this source (the query in step 4 above counted these as "populated columns").

meeting_point_notes

  • Type: string
  • Description: Free-text pickup/meeting-point instructions — supports detail_booking_notes-style display, though not merged into that named field for this source.
  • How built: From Stage 1's defaultPickupLocationWeb_clean, which strips leading/trailing whitespace off raw defaultPickupLocationWeb (13/24 rows populated).
  • Example: Hotel and pick up time to be confirmed

booking_lead_time

  • Type: number (hours, decimal)
  • Description: How much advance notice booking requires.
  • How built: From Stage 1's webLeadTime_clean, which nulls out negative sentinel values (-1, -8) found in the raw webLeadTime column; 15/24 rows populated once cleaned.
  • Example: 0.00

validity_start / validity_end

  • Type: string
  • Description: Labels describing the product's validity window (not actual dates — these are the labels used for the window's start/end, e.g. what "Day 1" and "Day N" are called for this product).
  • How built: Direct from raw termFirstDay / termLastDay (100% filled; observed values "Departing"/"Visit Date" and "Returning"/"End Date").
  • Example: validity_start = "Departing", validity_end = "Returning"

availability

  • Type: number
  • Description: Real availability/scheduling capacity figure.
  • How built: Direct from raw availability, renamed straight through (19/24 rows populated; values range from 0 to 99999).
  • Example: 1

operator_code

  • Type: string
  • Description: Internal operator code (distinct from the human-readable meta_supplier_name).
  • How built: From Stage 1's opcName_clean, a type-guard companion of raw opcName (some values look numeric, e.g. "69001" for Sydney Zoo products; the _clean column exists to flag/preserve these as text rather than let a downstream loader auto-cast them to numeric — the value itself is unchanged from the raw).
  • Example: SKYUP

booking_channel_code

  • Type: string
  • Description: Internal operator/booking-channel code, a separate identifier from operator_code.
  • How built: Direct from raw ocb (100% filled; 5 distinct values across the 24 products, e.g. ADAMSROTT, LANCELIN, SKYAPI).
  • Example: SKYAPI

return_time / departure_time_display

  • Type: string (clock time)
  • Description: Scheduled return and departure times — real scheduling data, distinct from the always-blank detail_start_time above.
  • How built: Direct from raw returning / departing respectively (both 100% filled).
  • Example: return_time = "12:01 AM", departure_time_display = "12:01 AM"

fare_types

  • Type: string (JSON-encoded list)
  • Description: Per-fare-tier pricing and booking rules (Adult, Child, Infant, Family, etc.) — CustomLinc's richest content field and the source of the derived product_price. Kept as a single JSON-string column (not flattened) since the list length varies per row (4–6 tiers).
  • How built: Direct from raw fareTypes, renamed straight through, no cleaning applied — including one known embedded-HTML quirk: some tiers' nested farePrompt sub-field contains a literal <br> tag (e.g. "<br>(Please select 1 Family when booking for 2 Adults and 2 Children)" on both Skyrail products' Family tier). This was flagged as an open UNCERTAIN item in reports/customlinc_stage2_column_selection.md and, per the actual build_customlinc_stage2.py code, was not cleaned — the <br> passes through as-is inside the JSON string.
  • Example (excerpt, SK1130QR4PUC): [{"code": "ADULT", ..., "priceGross": 132, ...}, {"code": "CHILD", ..., "priceGross": 66, ...}, {"code": "INF", ..., "priceGross": 0, ...}, {"code": "FAMILY", ..., "priceGross": 330, "farePrompt": "<br>(Please select 1 Family when booking for 2 Adults and 2 Children)", ...}]

package_type

  • Type: string
  • Description: How to interpret package_groups for this row (only meaningful where package_groups is also populated).
  • How built: Direct from raw packageType (4/24 rows populated: values "Package" or "Undefined").
  • Example: Package

is_pickup_compulsory

  • Type: boolean
  • Description: Whether a pickup location must be selected to book — real booking-rule flag.
  • How built: Direct from raw isPickupCompulsory, 100% filled.
  • Example: True

pickup_locations_general

  • Type: string (JSON-encoded list)
  • Description: General reference list of named pickup points (hotels, landmarks) available for this product — the top-level pickup list, distinct from the richer nested copy inside package_groups (see below).
  • How built: Direct from raw top-level pickupLocations, renamed straight through (8/24 rows populated). Per reports/customlinc_5_examples.md's comparison, this top-level list references the same underlying location catalog as the nested copy (same IDs/names/coordinates) but its transfers array is always empty/null — i.e. it carries no per-fare-type pickup-surcharge pricing.
  • Example (SK1130QR4PUC): 73 named pickup points around Cairns (e.g. {"code": "1", "description": "181 The Esplanade (pick up Cairns Queenslander)", "id": 1104, ..., "transfers": null}).

package_groups

  • Type: string (JSON-encoded list, up to 4 levels deep)
  • Description: Nested package/bundle structure — packageGroups → packageItems → pickupLocations → transfers. The transfers array at the deepest level carries real per-fare-type pickup-surcharge pricing (Adult/Child/Concession/Family/Infant) that the top-level pickup_locations_general never has.
  • How built: Direct from raw packageGroups, renamed straight through, kept as a single JSON-string column rather than flattened (only 4/24 rows populated: the item count varies per row, so flattening to fixed columns would require an arbitrary max-depth/max-fanout decision that was deliberately deferred, per the Stage 2 selection report).
  • Example (SK1130QR4PUC, first pickup entry inside the nested structure): {"code": "TBA", "description": " Hotel and pick up time to be confirmed", ..., "pickupScheduleOid": "3040.6923", "time": "/Date(-62135596740000)/", "transfers": [{"code": "Adult", "priceGross": 13.5, "priceNet": 10.8}, {"code": "Child", "priceGross": 13.5, ...}, {"code": "Concession", "priceGross": 0, ...}, {"code": "Family", "priceGross": 54, ...}, {"code": "Infant", "priceGross": 0, ...}]}

departure_date

  • Type: string (ISO date, YYYY-MM-DD)
  • Description: A real forward-looking departure date — not a placeholder, unlike detail_start_time's source field.
  • How built: Derived at Stage 2 by parse_dotnet_date() from raw departureDate, which stores a .NET /Date(ms)/ epoch string (/Date(1783900800000)/ on all 24 rows in this snapshot). Parsed to a UTC date via datetime.fromtimestamp(ms/1000, tz=utc).date().
  • Example: 2026-07-13

Fields CustomLinc Does NOT Populate

Per the unified schema table in CLAUDE.md, CustomLinc is documented as a source for several fields that turn out to carry zero actual data once traced to the real raw JSON — confirmed both in reports/customlinc_column_analysis.md (100% empty across all 24 rows) and by their absence from data_pipeline/stage2/customlinc_stage2.csv's COLUMN_RENAME list:

  • detail_description — CustomLinc has no description field of any kind. Raw webLongDesc, webShortDesc, and webpageDesc are all 100% empty across all 24 rows — confirmed the weakest source in the project, as documented in CLAUDE.md's source-quality table ("Weak — no description in detail API").
  • detail_what_is_included — documented source is raw fareIncludes, which is 100% empty across all 24 rows. The column was excluded from Stage 2's COLUMN_RENAME entirely (never reaches unified_products.csv for this source), unlike, say, Fareharbor's always-empty-but-still-mapped fields.
  • detail_booking_notes — documented source is raw alert, also 100% empty across all 24 rows, and likewise excluded from COLUMN_RENAME.
  • detail_languages — documented source is raw languageName, also 100% empty, also excluded from COLUMN_RENAME.
  • location_city / location_state / location_country / location_postcode / location_latitude / location_longitude — none of these have a documented CustomLinc source in CLAUDE.md's Source Field Mapping table to begin with (only location_street does), and none exist in the Stage 2 output.
  • detail_return_time — documented as a CustomLinc-only field per the Figma-mapped DETAIL PAGE table, but there is no COLUMN_RENAME entry producing a unified field with this exact name; the closest analog kept is the non-schema-named return_time (from raw returning), which is real populated data (100% filled) but was never renamed to the schema's documented detail_return_time label. This looks like a naming gap between the schema-design doc and the actual Stage 2 build, worth flagging to whoever owns the unified schema.
  • product_headline, product_images, product_tags — no raw CustomLinc field maps to any of these; CustomLinc is not listed as a source for them in CLAUDE.md's LISTING PAGE table either.

Fields Documented But Not Selected for the Unified Schema

These raw/Stage-1 columns exist in customlinc_stage1.csv (70 columns total) but were deliberately excluded from customlinc_stage2.csv's COLUMN_RENAME list (27 entries), so they never reach unified_products.csv. Listed here so a reader who finds them in an earlier pipeline stage doesn't wonder where they went:

22 columns are 100% empty across all 24 rows (per reports/customlinc_column_analysis.md): acType, alert (documented mapping to detail_booking_notes but no data), defaultPromoCode, dropoffLocations, fareIncludes (documented mapping to detail_what_is_included but no data), image, imageCaption, languageName (documented mapping to detail_languages but no data), lowestPriceFareTypeCode, lowestPriceFareTypeShortName, nights, origins, priceOrigins, productOptions, surchargeCodes, vehicles, webContent, webLongDesc, webShortDesc, webpageDesc, webpageKeywords, webpageTitle.

Superseded-by-_clean-companion originals (the raw column exists in Stage 1 but only the cleaned companion was selected for Stage 2): code (superseded by _filename_product_id → product_id; the two agree on all 24/24 rows, but _filename_product_id was chosen as the authoritative ID per the cleaning checklist's recommendation), name (→ name_clean), duration (→ duration_minutes), defaultDepartureDate and defaultDepartureDate_clean (100% placeholder-epoch dates, no real data — neither version was selected), departureTime (→ departureTime_clean, though as noted above the cleaned version is itself 100% blank for this source), defaultPickupLocationWeb (→ defaultPickupLocationWeb_clean), opcName (→ opcName_clean), webLeadTime (→ webLeadTime_clean).

Internal ETL bookkeeping, not product data: _source_filename.

Zero-variation flag/financial fields — real columns with data in every row, but every row has the identical value (all False or all 0 in this 24-row sample), so there is currently nothing for the unified schema to differentiate on: areFaresPOA (24/24 False), areNamesRequired (24/24 False), isNameCompulsory (24/24 False), isWeightCompulsory (24/24 False), expiryMonths (24/24 0), yield (24/24 0), yieldVehicle (24/24 0), yieldVehicleUnits (24/24 0). Per reports/customlinc_stage2_column_selection.md, these were flagged as UNCERTAIN rather than confidently excluded — future CustomLinc pulls may show real variation.

endLocation — identical to startLocation/location_street wherever either is populated (2/24 rows); not a second data point, so it was not carried forward.
