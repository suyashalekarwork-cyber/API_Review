Column Reference / Ingresso

Ingresso — Unified Schema Field Reference

  • Scope: Every unified-schema column that Ingresso actually populates in data_pipeline/unified_database/unified_products.csv (source = "Ingresso"). Ingresso supplies 21 of the 87 unified columns (22 counting source itself); the rest are always blank for this source and are not documented here.
  • Audience: Team members looking up what a field means and where it comes from. This is NOT a data-quality report — for null rates, outliers, and QA flags see reports/ingresso_column_analysis.md instead.

Ingresso is small and structurally different from the other 6 sources: only 16 products total (data/Ingresso/*.json), and its raw API is fundamentally a pricing/availability feed (deep cost_range/avail_details nesting) rather than a content feed — most of its 104 raw columns are booking-engine internals (tax components, availability bitmasks, add-on flags) with no unified-schema home. CLAUDE.md's summary table calls Ingresso "Poor — no description or images," which is correct for images (confirmed: zero image fields anywhere in the raw data) but only partially true for description — see detail_description below.

Pipeline stages behind this doc

etl_ingresso.py

reads data/Ingresso/*.json (16 files), normalizes the two dynamic-key structures (see below), flattens everything into dot-notation columns, writes exports/ingresso_etl_v1.csv (99 columns). Zero cleaning/dropping.

scripts/build_ingresso_stage1.py

reads the ETL output, adds 5 HTML-stripped *_clean companion columns plus one type-guard companion (event_code_clean); every original column is kept untouched. Writes exports/ingresso_stage1.csv, mirrored at data_pipeline/stage1/ingresso_stage1.csv (104 columns) — the Stage 2 script reads from the data_pipeline/stage1/ copy.

scripts/build_ingresso_stage2.py

selects/renames 19 columns to unified names via a fixed COLUMN_RENAME list, plus derives product_category from 4 boolean class flags. Writes data_pipeline/stage2/ingresso_stage2.csv (20 columns, 16 rows).

scripts/build_unified_database.py

folds Stage 2 into unified_products.csv. Ingresso is in SOURCES with needs_source_col=True (it carries no native source field, unlike Rezdy/Fareharbor), so the literal string "Ingresso" is added. Also applies the shared normalize_currency() (uppercase), normalize_country() (2-letter codes pass through, full names mapped via a small lookup table), normalize_category() (JSON-string list of category names, uniform shape across all 7 sources), and derive_price_numeric() (Ingresso's product_price is already a scalar, so this is just float(product_price) passed straight through).

  • Example product used throughout: product_id = 1D9A0 ("Sea Life Melbourne General Admission", supplier merlin_apac_sealife_melbourne) — chosen because, unusually for this source, it has real non-blank values in detail_description AND detail_booking_notes simultaneously (most of the 16 products have at most one of the two populated). A second product, product_id = 1DJRR ("Sea Life Kelly Tarlton's Auckland General Admission"), is used for location_street, since that field is populated on only 1 of the 16 rows and 1D9A0 isn't the one.

The Dynamic-Key Normalization (read this before the field list)

Ingresso's raw JSON has two structures keyed by a value that varies per product, not by a fixed field name:

  • events_by_id — keyed by the event code (e.g. "1DJRR", "1D9A0")
  • currency_details — keyed by the currency code (e.g. "aud", "nzd")
{"events_by_id": {"1DJRR": {"event": {...}}}}
{"currency_details": {"aud": {"currency_code": "aud", ...}}}

Flattening either of these naively would bake the per-product dynamic key into the column NAME itself (e.g. a column literally called events_by_id.1DJRR.event.event_desc), so every product would end up with its own unique set of columns instead of aligning on shared fields across the dataset — which would make the CSV unusable for anything but single-row lookups.

etl_ingresso.py::normalize_dynamic_key_dict() fixes this by replacing each dynamic key with a fixed positional key (event_1, currency_1 — 1-indexed, in source-file order) before flattening, and preserving the original dynamic key in a companion .raw_key field:

{"events_by_id": {"event_1": {"event": {...}, "raw_key": "1DJRR"}}}
{"currency_details": {"currency_1": {"currency_code": "aud", "raw_key": "aud"}}}

That's why every raw Ingresso column in the pipeline is named events_by_id.event_1.event.* or currency_details.currency_1.* — the event_1/currency_1 segment is NOT a real API field, it's this normalization's fixed placeholder. All 16 files were verified to have exactly one entry under each of events_by_id/currency_details, so the positional scheme currently produces only event_1/currency_1, but it's written to handle a future product with multiple entries under either key correctly (it would produce event_2, event_3, etc.). This is also why the CLAUDE.md schema-mapping table's raw-field notation (events_by_id.*.event.venue_addr → location_street, .city_desc → location_city, .country_desc → location_country, .postcode → location_postcode, .geo_data.latitude/.longitude → location_latitude/location_longitude, .source_code → meta_supplier_id, .source_desc → meta_supplier_name) uses a wildcard * in place of the dynamic key — in the actual pipeline that * is always event_1.

Identity

product_id

  • Type: string (5-char alphanumeric event code)
  • Description: Ingresso's unique product identifier.
  • How built: Parsed from the source filename (Ingresso-{venueCode}-{productId}.json) via parse_product_id_from_filename(), which joins everything after the first two hyphen segments. Cross-checked against the event's own internal ID (events_by_id.event_1.event.event_id, and the dynamic key itself, events_by_id.event_1.raw_key) — all three agree on all 16 files, unlike CustomLinc where the filename rule broke on 12/24 files.
  • Example: 1D9A0

source

  • Type: string (constant)
  • Description: Marks which of the 7 supplier systems this row came from.
  • How built: Hardcoded literal "Ingresso", added at the build_unified_database.py merge step — Ingresso's raw API carries no native source/supplier-system field of its own (needs_source_col=True in SOURCES).
  • Example: Ingresso

event_code

  • Type: string (not a formally documented unified field, but selected and carried through — see note below)
  • Description: Ingresso's own internal ticket/event code, distinct from product_id.
  • How built: Raw events_by_id.event_1.event.event_code, via its Stage 1 _clean companion (event_code_clean) — a type-guard fix, not a content change: one value in the 16-row sample ("66") looks numeric, and the _clean companion forces it to stay a string so a downstream loader (e.g. pandas dtype inference) doesn't silently cast it to int.
  • Example: n/10522

Listing Page Fields

product_name

  • Type: string
  • Description: Full product/ticket name.
  • How built: Direct from raw events_by_id.event_1.event.event_desc (100% filled across all 16 products).
  • Example: Sea Life Melbourne General Admission

product_price / product_price_numeric

  • Type: number (decimal, in the currency given by product_currency)
  • Description: Starting price for the product.
  • How built: product_price comes from events_by_id.event_1.event.cost_range.min_seatprice. This was a judgment call documented in reports/ingresso_stage2_column_selection.md: in this 16-row sample, min_seatprice, max_seatprice, min_combined, and max_combined are numerically identical on every row (every product here is a fixed-single-price ticket with zero surcharge), so the specific choice among the four is currently moot — min_seatprice was picked as the "starting price" convention to match how price is derived for Rezdy/Fareharbor/CustomLinc/Ventus. product_price_numeric is the unified-database companion column added for every source (derive_price_numeric()); for Ingresso this is just float(product_price) passed straight through, since the value is already a scalar (unlike Livn's {amount, currency} object).
  • Example: 33.0

product_currency

  • Type: string (ISO code)
  • Description: Currency the price is quoted in.
  • How built: Raw events_by_id.event_1.event.cost_range.range_currency_code, uppercased at the build_unified_database.py merge step (normalize_currency()). A separate, unselected field — currency_details.currency_1.currency_code — carries the same value and was kept only as a supporting/cross-check column in Stage 2 discussions, not selected into the unified schema itself.
  • Example: aud (raw) → AUD (unified)

product_category

  • Type: JSON-string list of category-name strings
  • Description: Tour/ticket type classification.
  • How built: This is the field CLAUDE.md's build_unified_database.py docstring calls out as "Ingresso's already-list-of-strings" shape — verified true, but only because Stage 2 constructs it that way, not because Ingresso's raw API has a native list field. build_ingresso_stage2.py's derive_product_category() builds the list itself from 4 independent boolean flags (events_by_id.event_1.event.classes.attractions, .passes, .family, .themeparks — confirmed non-exclusive, e.g. a product can be both Attractions and Family), appending the flag's label wherever the raw value is non-blank, and writes the result as json.dumps(tags). So by the time normalize_category() in build_unified_database.py sees it, it's already a JSON list of plain strings and passes straight through the isinstance(item, str) branch unchanged — no dict-unwrapping or single-string-wrapping logic actually fires for Ingresso, even though the function is written to handle those cases for other sources (Livn's {id,name} objects, CustomLinc/Ventus's plain strings).
  • Example: ["Attractions", "Passes"]

Location Fields (Details API only, per Critical Rule #8)

location_city

  • Type: string
  • Description: City.
  • How built: Direct from raw events_by_id.event_1.event.city_desc, per CLAUDE.md's Source Field Mapping table. Populated on 12 of 16 rows (the 4 Sydney-attraction-pass products have no city_desc in the raw payload).
  • Example: Melbourne

location_country

  • Type: string (2-letter ISO code after normalization)
  • Description: Country.
  • How built: Direct from raw events_by_id.event_1.event.country_desc (100% filled, raw values are full names: "Australia", "New Zealand", "United States of America"), mapped to ISO-2 at the build_unified_database.py merge step via normalize_country()'s COUNTRY_NAME_TO_ISO lookup table.
  • Example: Australia (raw) → AU (unified)

location_postcode

  • Type: string (includes a state/region prefix, not a bare postcode)
  • Description: Postcode.
  • How built: Direct from raw events_by_id.event_1.event.postcode (100% filled). Note the raw value is not a bare numeric postcode — it's a combined "{state/region} {code}" string (e.g. "VIC 3000", "NZ 1071"), passed through unchanged; no unified-schema field currently separates the state/region portion out for Ingresso.
  • Example: VIC 3000

location_latitude / location_longitude

  • Type: number
  • Description: GPS coordinates.
  • How built: Direct from raw events_by_id.event_1.event.geo_data.latitude / .longitude (100% filled).
  • Example: -37.81824, 144.96489

location_street

  • Type: string
  • Description: Street address.
  • How built: Raw events_by_id.event_1.event.venue_addr_html, via its Stage 1 _clean companion (venue_addr_html_clean, HTML-stripped per CLAUDE.md's block-tag-boundary pattern). Populated on only 1 of 16 rows — confirmed during Stage 2 review that a second raw field, structured_info.address.value_html, carries byte-for-byte identical text on the one row where both are populated, so it's a duplicate of the same underlying value, not an independent second source; venue_addr_html_clean was kept as the single primary field and structured_info.address.* was dropped. Kept despite the low fill rate on the reasoning that a sparse-but-real field is more useful to the unified schema than an artificially absent one.
  • Example (product 1DJRR, not the running example above — this is the one row where the field is populated): 23 Tamaki Drive, Orakei, Auckland NZ 1071

Detail Page Fields

detail_description

  • Type: string
  • Description: "About the Experience" section.
  • How built: Raw events_by_id.event_1.event.event_info_html, via its Stage 1 _clean companion (event_info_html_clean, HTML-stripped). Populated on only 3 of 16 rows. A second raw field, structured_info.overview.value_html, was confirmed to carry byte-for-byte identical text wherever both are populated, so it's the same underlying content duplicated, not an independent source, and was dropped in favor of event_info_html_clean (which has the slightly better fill rate — 3/16 vs. 2/16, because product 1DJRR's address text only appears under event_info, not under structured_info.overview). This is the field that makes CLAUDE.md's "no description" characterization only partially accurate — real prose description content exists for a minority of products, it's just sparse, not literally absent.
  • Example: "SEA LIFE Melbourne gives you up-close encounters with some of the world's most incredible animals, including adorable penguins, huge sharks, massive crocodiles, mysterious stingrays and thousands of tropical fish. Booking online is the best way to guarantee entry (spots are very limited)."

detail_booking_notes

  • Type: JSON-string list of objects (not plain text, unlike this field for other sources)
  • Description: Important Information / ticket-redemption instructions.
  • How built: Raw events_by_id.event_1.event.custom_field — kept as the raw JSON-list string per the project's list-field pattern (each entry is a {custom_field_data, custom_field_data_html, custom_field_name} object; the "self_print_ticket_text" custom field is the one that actually carries content). Populated on 7 of 16 rows, all real ticket-redemption/entry instructions (e.g. "please go straight to the main entrance..."), confirmed genuinely distinct content from detail_description/event_info rather than a duplicate. On the other 9 rows the raw value is a literal empty list "[]", which is present but carries no content — worth checking for that literal [] rather than treating it as populated when computing fill rates.
  • Example: [{"custom_field_data": "", "custom_field_data_html": "<p>With your e-ticket or mobile ticket, please go straight to the main entrance to start your experience</p>", "custom_field_name": "self_print_ticket_text"}]

Meta Fields (internal, not shown to customers)

meta_supplier_id

  • Type: string
  • Description: Supplier account ID.
  • How built: Direct from raw events_by_id.event_1.event.source_code (100% filled), per CLAUDE.md's Source Field Mapping table.
  • Example: merlin_apac_sealife_melbourne

meta_supplier_name

  • Type: string
  • Description: Supplier company name.
  • How built: Direct from raw events_by_id.event_1.event.source_desc (100% filled), per CLAUDE.md's Source Field Mapping table.
  • Example: Merlin Sea Life Merlbourne (raw supplier-provided text, including its typo — passed through unchanged, not corrected by the pipeline).

Fields Selected But Not Part of the Documented 43-Field Unified Schema

These columns made it into unified_products.csv for Ingresso — they're real, populated data, not pipeline artifacts — but they don't correspond to one of the 43 named unified fields in CLAUDE.md's schema tables. They exist because build_ingresso_stage2.py's COLUMN_RENAME list carried them through as useful supporting context for a source with very little else to offer:

  • venue_name — the venue's display name (e.g. "SEA LIFE Melbourne"), 100% filled and Ingresso's most reliable location-identifying text, but distinct from any of location_street/location_city.
  • ticket_type_details — the full nested avail_details.ticket_type JSON-list structure (pricing tiers, availability windows, tax components), kept as supporting detail for the Pricing section even though there's no single unified field for it.
  • is_seated — boolean flag on whether the ticket is for a seated event (always False across this 16-row sample).
  • valid_quantities — JSON list of bookable quantities per order (always [1..20] across this sample).

Fields Ingresso Does NOT Populate

Per the unified schema table in CLAUDE.md, Ingresso is documented as a source for the following fields, but none of them are present in ingresso_stage2.csv's COLUMN_RENAME list, so none of them appear in unified_products.csv for this source. This is the expected, documented shape of the weakest of the 7 sources — Ingresso only supplies 21 of 87 unified columns, by far the fewest of any source:

Listing Page fields: product_headline, product_duration, product_images, product_main_image, product_tags

Location fields: location_state (Rezdy-only per the schema anyway)

Detail Page fields (all of them): detail_highlights, detail_what_is_included, detail_what_is_not_included, detail_itinerary, detail_accessibility, detail_cancellation_policy, detail_operating_days, detail_start_time, detail_return_time, detail_languages, detail_health_safety, detail_min_age, detail_max_age, detail_group_size, detail_tax_percentage, detail_tripadvisor_rating, detail_google_rating, detail_what_to_bring

Meta fields: meta_supplier_website, meta_supplier_email, meta_supplier_phone (all three are Livn-only per the schema anyway)

Of particular note: product_images is genuinely absent from the raw API — confirmed no image/images/photo field exists anywhere in the 16 raw JSON files, at any nesting depth. This part of CLAUDE.md's "no description or images" characterization holds up completely; only the "no description" half needed the correction documented under detail_description above.

Fields Documented But Not Selected for the Unified Schema

These raw/Stage 1 columns exist in data_pipeline/stage1/ingresso_stage1.csv (104 columns total) but were deliberately excluded from ingresso_stage2.csv's 20-column COLUMN_RENAME/derivation list, so they never reach unified_products.csv. Listed here so a reader who finds them in an earlier pipeline stage doesn't wonder where they went. Full detail and reasoning for every one of these lives in reports/ingresso_stage2_column_selection.md; summarized by group:

  • Raw pre-_clean counterparts — event_info, event_info_html, venue_addr, venue_addr_html, event_code (raw) — superseded by their Stage 1 _clean companions, which ARE selected (event_info_html_clean → detail_description, venue_addr_html_clean → location_street, event_code_clean → event_code).
  • structured_info.overview.* and structured_info.address.* (6 columns) — confirmed byte-for-byte duplicate content of event_info_html_clean/venue_addr_html_clean respectively wherever both are populated; dropped as fully redundant, not because the content itself is unwanted.
  • The no_singles_cost_range.* group (14 columns) — confirmed numerically identical to the parent cost_range.* fields on every row in this 16-row sample; excluded to avoid ~14 duplicate columns, though this could diverge for a future product with different pricing rules.
  • cost_range.max_seatprice / .min_combined / .max_combined — confirmed identical to min_seatprice (which IS selected as product_price) across this sample; not carried forward separately.
  • Internal pricing-engine metadata — cost_range.alternate_discounts, .approx_last_seen_iso8601_date_and_time, .discount_semantic_type, .max_combined_combined_tax_component, .max_combined_surcharge_tax_sub_component, .max_surcharge, .min_combined_combined_tax_component, .min_combined_surcharge_tax_sub_component, .min_surcharge, .valid_quantities (cost_range-level duplicate of the already-selected events_by_id.event_1.valid_quantities), cost_range_details.ticket_type (duplicate of the selected avail_details.ticket_type) — supports pricing math internally but not customer-facing content.
  • Internal booking-flow/configuration flags (all 100% filled booleans, always constant across the 16-row sample) — add_ons, upsells, custom_filter, early_horizon, late_horizon, has_no_perfs, is_add_on, is_auto_quantity_add_on, is_date_matched_add_on, is_time_matched_add_on, need_departure_date, need_duration, need_performance, venue_is_enforced, show_perf_time, event_lingo_settings.event_lingo.
  • Internal reference/routing metadata — event_id (redundant with product_id), event_path, event_uri_desc, venue_uri_desc, event_subdata, event_status, main_class_key (redundant with the classes.* flags that feed product_category), perf_offsale_delay_seconds (only 1/16 rows populated).
  • Sparse/low-value classification flags — classes.family, classes.themeparks (both only 1/16 rows populated — folded into product_category's derivation logic alongside classes.attractions/ classes.passes rather than surfaced as standalone columns).
  • Currency supporting/internal fields — currency_details.currency_1. currency_code (duplicate of the selected cost_range.range_currency_code), .currency_factor, .currency_number, .currency_places (conversion/ formatting metadata), .currency_post_symbol (100% empty — Ingresso only uses pre-symbols like "$", never post-symbols), .raw_key.
  • ETL/normalization bookkeeping — events_by_id.event_1.raw_key, currency_details.currency_1.raw_key (the dynamic-key-preservation columns described above — internal to the pipeline, not product content), _source_filename (original JSON filename).
  • The trailing-dot vestigial field — event_lingo_settings. event_lingo_options. (note the literal trailing dot in the column name: the raw JSON key under event_lingo_options is itself an empty string, {"event_lingo_options": {"": true}}, which the flattener faithfully reproduced as a malformed column name; always True across all 16 rows, carries no distinguishing information — likely vestigial in Ingresso's own API, not something this pipeline should propagate further).
  • event_type (simple_ticket/misc_item) — a real, 100%-filled booking-mechanics classification, but per build_ingresso_stage2.py's own docstring it was deliberately kept separate from and excluded in favor of the classes.*-derived product_category, since it describes booking mechanics rather than product category.
