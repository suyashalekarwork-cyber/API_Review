Column Reference / Livn

Livn — Unified Schema Field Reference

  • Scope: Every unified-schema column that Livn actually populates in data_pipeline/unified_database/unified_products.csv (source = "Livn"). Livn supplies 35 of the 87 unified columns (167 rows); the rest are always blank for this source and are not documented here.
  • Audience: Team members looking up what a field means and where it comes from. This is NOT a data-quality report — for null rates, outliers, and QA flags see reports/livn_column_analysis.md instead.

Pipeline stages behind this doc

etl_livn.py

reads data/Livn/*.json (167 files, raw root object, no nesting key like Rezdy/TDU's "product" or Fareharbor's "item"), flattens nested dicts into dot-notation columns and JSON-stringifies lists, writes the 86-column raw base to exports/livn_etl_v1.csv. Zero cleaning/dropping. Product ID parsed from the filename (Livn-{supplierId}-{productId}.json) as the last hyphen segment via parse_product_id_from_filename() — but note the real product_id used downstream is the raw JSON's own id field, not the filename parse (see Identity section below).

scripts/build_livn_stage1.py

writes data_pipeline/stage1/livn_stage1.csv (88 columns — 2 more than the raw ETL, from 2 added _clean companion columns: supplier.tnc_clean and supplier.state_clean). No columns dropped or renamed per Stage 1 rule.

reports/livn_stage2_column_selection.md

SELECTED/PAIRED/NOT SELECTED/UNCERTAIN column report; confirmed with the user before build.

reports/livn_specialnotes_duration_check.md

a follow-up label-frequency analysis of specialNotes's internal Label:\n structure, and a relevance check on durationRangeMax/timeStartRangeMax, both of which fed directly into the Stage 2 build logic below.

scripts/build_livn_stage2.py

writes data_pipeline/stage2/livn_stage2.csv (33 columns): renames columns to unified names, extracts locationsStart[0] into 6 scalar location_* columns, and runs a regex-based parser over specialNotes to split it across 3 destination fields (see detail_what_to_bring / detail_what_is_not_included / detail_booking_notes below).

scripts/build_unified_database.py

folds Stage 2 into unified_products.csv. Livn is listed in SOURCES with needs_source_col=True (its Stage 2 CSV has no native source column, unlike Rezdy/Fareharbor, so this step adds the literal "Livn" value fresh). This step also derives product_price_numeric (Livn-specific unwrap logic — see product_price below) and normalizes product_category from Livn's {id, name} object-list shape into a plain JSON list of category-name strings via normalize_category().

  • Example product used throughout: product_id = 72 ("Moreton Island Get Wrecked 1 Day Tour", supplier Australian Sunset Safaris) — chosen because it has real, non-empty values in more populated fields than any other Livn row (6 of the sparser/optional fields all present at once). A second product, product_id = 62543 ("Cairns Boat Hire 8 Man Pontoon"), is used for product_duration_range_max / detail_start_time_range_max, which are blank on product 72.

Identity

product_id

  • Type: string (numeric-looking, e.g. "72")
  • Description: Livn's unique product identifier.
  • How built: Direct from raw JSON field id (Stage 2 COLUMN_RENAME: id → product_id). This is Livn's own internal ID, not derived from the filename — though for Livn the two agree in every file observed (the _filename_product_id companion column exists in Stage 1 for cross-checking but was not selected into the unified schema).
  • Example: 72

source

  • Type: string (constant)
  • Description: Marks which of the 7 supplier systems this row came from.
  • How built: Not present in livn_stage2.csv — added fresh as the literal "Livn" at the build_unified_database.py merge step (SOURCES entry has needs_source_col=True).
  • Example: Livn

product_name / product_name_original

  • Type: string
  • Description: product_name is the customer-facing display title; product_name_original is the supplier's own internal product name/booking-reference text.
  • How built: Direct rename of raw fields name → product_name and nameOriginal → product_name_original. These are a genuine two-source pair, not a duplicate-and-drop situation — per reports/livn_stage2_column_selection.md, they diverge in 127 of 167 rows (76%), re-verified directly against unified_products.csv. name was chosen as the primary/customer-facing field; nameOriginal is kept as a companion reference column rather than merged in, since concatenating a curated title with an internal booking name would produce an unusable display string.
  • Example: product_name = "Moreton Island Get Wrecked 1 Day Tour" (identical to product_name_original for this particular product — the divergent case is e.g. product 144, name="Army Duck with Skyrail & Train ex Cairns" vs nameOriginal="Kuranda Army Duck Experience (0850 Train) Army Duck (1515 Skyrail)").

Listing Page Fields

product_price / product_price_numeric

  • Type: product_price = JSON-list-as-string of {amount, currency} objects; product_price_numeric = number
  • Description: Starting price for the product. Livn is the only source where product_price is not already a plain scalar.
  • How built: product_price is a direct rename of raw field fromPrices (always exactly 1 item across all 167 rows, but kept as a list for schema consistency with other list-valued fields). At the unified-database merge step, derive_price_numeric() special-cases source_name == "Livn": it json.loads()s the string, and if it parses to a list of dicts, extracts .get("amount", "") from the first entry. Every other source's product_price is treated as already-scalar and just float()-cast through.
  • Example: product_price = '[{"amount": 189, "currency": "AUD"}]', product_price_numeric = "189"

product_category

  • Type: JSON-list-as-string of category-name strings
  • Description: Tour type/category tags.
  • How built: Raw field categories (a JSON list of {"id", "name"} objects, 157/167 rows have >1 item) is carried through Stage 2 as-is under the unified name, then reshaped at the unified-database merge step: normalize_category() parses the JSON, and since each element is a dict, extracts just the name value from each, discarding id, so every source's product_category ends up in the same plain ["name1", "name2", ...] shape regardless of original structure.
  • Example: ["Full Day Trips & Excursions", "National Parks & Natural Attractions", "Activities"]

product_images

  • Type: JSON-list-as-string of {url, width, height, fileSize, mimeType} objects
  • Description: Gallery images.
  • How built: Direct rename of raw field images, kept as its full JSON structure (not flattened to bare URLs) — 166/167 rows populated, 1 row has an empty list.
  • Example: [{"url": "https://res.cloudinary.com/livngds/image/upload/v1692227791/V2/CENTRAL/productImages/72/kfop14nhganqhkrcghuq.jpg", "width": 1920, "height": 1440, "fileSize": 286635, "mimeType": "image/jpg"}, ...]

product_duration / product_duration_range_max

  • Type: number (minutes)
  • Description: How long the tour runs; _range_max is a companion max-duration for products with a variable/range duration (e.g. flexible self-drive rentals, multi-day packages).
  • How built: Direct renames of raw fields duration (100% filled) and durationRangeMax (only 26/167 rows, 15.6% — kept per the relevance check in reports/livn_specialnotes_duration_check.md, which found the sparse values are real min/max range data, not noise).
  • Example (product 72): product_duration = 1440 (24 hours); product_duration_range_max blank.
  • Example (product 62543, "Cairns Boat Hire 8 Man Pontoon"): product_duration = 240 (4h), product_duration_range_max = 11520 (192h/8 days — self-drive rental, hourly minimum to multi-day maximum).

Location Fields (Details API only, per Critical Rule #8)

location_source / location_end_source

  • Type: JSON-list-as-string
  • Description: Not named unified-schema fields themselves — the full raw location objects (with latitude, longitude, city, district, state, country, postcode, business, address1, etc.) kept as supporting/audit data behind the scalar location_* columns below. location_end_source (from raw locationsEnd) has no dedicated scalar unified field extracted from it — it's carried forward as raw JSON only, useful for itinerary/return-location display.
  • How built: Direct renames of raw fields locationsStart → location_source and locationsEnd → location_end_source.
  • Example: location_source = '[{"latitude": -27.997215421294463, "longitude": 153.429399049735, "tz": "Australia/Brisbane", ..., "city": "Gold Coast", "district": "Surfers Paradise", "state": "QLD", "country": "AU", ..., "business": "Mantra on View Hotel", "address1": "22 View St", "postcode": "4217"}]'

location_street, location_city, location_state, location_country, location_latitude, location_longitude

  • Type: string / number
  • Description: Structured, scalar address components extracted for display.
  • How built: Stage 2 parses locationsStart as JSON and takes only element [0] (the first location in the list — 3/167 rows have >1 location, so multi-stop routes lose everything after the first stop at this step). From that object: address1 → location_street, city → location_city, state → location_state, country → location_country, latitude/longitude → the coordinate columns. location_street is the sparsest of these (116/167 rows, 69.5%) since not every locationsStart[0] object carries an address1 key.
  • Example: location_street = "22 View St", location_city = "Gold Coast", location_state = "QLD", location_country = "AU", location_latitude = -27.997215421294463, location_longitude = 153.429399049735

Detail Page Fields

detail_description

  • Type: string (long text)
  • Description: "About the Experience" section.
  • How built: Direct rename of raw field description, 100% filled, passed through unchanged (no HTML in this field per the Stage 1 completeness check).
  • Example: "Moreton Island is a unique paradise of golden beaches, rolling surf and beautiful freshwater lakes. Join Sunset Safaris as we explore and snorkel the stunning Tangalooma Shipwrecks..." (contains a stray U+FFFD replacement character in place of an apostrophe in the raw source text — unrecoverable upstream data loss, not a pipeline bug, per CLAUDE.md's mojibake note.)

detail_highlights

  • Type: JSON-list-as-string of strings
  • Description: "Tour Highlights" section.
  • How built: Direct rename of raw field highlights.highlights (already a plain JSON array of highlight sentences, not objects), kept as a JSON string rather than flattened.
  • Example: ["Enjoy a beautiful cruise across the magnificent Moreton Bay on the MiCat Ferry with air-conditioned comfort with cafe and bar facilities", "Relax on the beach at the Tangalooma Wrecks and have fun in the sun", ...]

detail_what_is_included

  • Type: JSON-list-as-string of {content, [type]} objects
  • Description: "What's Included" section.
  • How built: Direct rename of raw field inclusions.items, kept as its full JSON structure (some entries carry an optional type, e.g. "TRANSPORT"/"MEALS", others don't).
  • Example: [{"content": "Fully Guided Tour"}, {"content": "Activities"}, {"content": "Snorkelling Equipment"}, ..., {"type": "TRANSPORT", "content": "Return Bus Transfers"}, {"type": "MEALS", "content": "Lunch"}]

detail_itinerary

  • Type: JSON-list-as-string of {dayFrom, dayTo, title, body} objects
  • Description: Cruise Route / Itinerary section.
  • How built: Direct rename of raw field itinerary.items. Sparse — 157/167 rows are an empty list []; only 9 rows have real itinerary entries (max 12 items in one row).
  • Example (product 72): [] (empty for this product — its schedule information lives in detail_operating_days/detail_start_time instead).

detail_what_is_not_included

  • Type: string (long text, may be a " | "-joined concatenation)
  • Description: What's Not Included section.
  • How built: Not a direct API field — Livn has no dedicated "not included" field. Stage 2's parse_special_notes() function splits the free-text specialNotes field on its internal Label:\n structure (regex LABEL_RE); any section whose label matches NOT_INCLUDED_LABELS ("not included") is routed here, multiple matching sections joined with " | ". Sparse — only 9/167 rows have a detected "Not included" section (matches the label-frequency count in reports/livn_specialnotes_duration_check.md).
  • Example: "POB National Park and Ferry Fees (To be paid in cash upon departure). Per person Adult AUD $80 and Children 13 years and under AUD $60. Pick-up and Drop-off in different regions attract additional fees."

detail_what_to_bring

  • Type: string (long text, may be a " | "-joined concatenation)
  • Description: What To Bring section.
  • How built: Same specialNotes label-parser as above — sections labeled "what to bring" or "what to wear" (WHAT_TO_BRING_LABELS) are routed here. 138/167 rows (82.6%) have a detected section (re-verified directly against the live script run, matches the value in reports/livn_specialnotes_duration_check.md's 141-row estimate closely — the small gap is because a few label variants like "What to Wear" map to the same bucket but the script's exact-match set only counts label text after lowercasing/stripping).
  • Example: "Water bottle, swimwear, sunscreen, beach towel, hat, camera, flip flops/thongs, walking shoes and insect repellant."

detail_booking_notes

  • Type: string (long text, " | "-joined concatenation of up to 4+ sources)
  • Description: Important Information section.
  • How built: A real multi-source concat, not a single field: raw pickupNotes + raw dropoffNotes + a formatted "ABN: {supplier.businessNumber}" string (only when a business number exists) + every catch-all section from the specialNotes parser (any label that isn't "what to bring"/"what to wear"/"not included" — e.g. Conditions, Optional extras, Fuel Surcharge/Levies, Health and Safety, or unlabeled leading text — falls into this catch-all bucket by design, since enumerating every label variant wasn't necessary once a fallback bucket existed). Every non-empty piece is joined with " | " in that fixed order. The catch-all bucket fires on effectively every row (167/167, since Conditions: is present in 100% of specialNotes values per the specialNotes check report).
  • Example (truncated): "Please note that during the month of April and May 2025 pick-up times will vary due to a change to the ferry schedule.\n\nPick-up options:\nGold Coast: \nDeparts 05:45 from Mantra on View Hotel..." (this is the pickupNotes portion; dropoffNotes and the specialNotes catch-all sections are appended after it with " | " separators.)

detail_group_size

  • Type: number
  • Description: Group Size field.
  • How built: Direct rename of raw field groupSizeMax. Very sparse — only 7/167 rows (4.2%) populated, but real data when present.
  • Example: 24

detail_min_age

  • Type: number
  • Description: Minimum Age field.
  • How built: Direct rename of raw field ageMin. Sparse — 33/167 rows (19.8%) populated.
  • Example: 4

detail_operating_days

  • Type: string (comma-separated day abbreviations)
  • Description: Schedule section — which days of the week the tour runs.
  • How built: Direct rename of raw field operatingDaysStr (the human-readable form, e.g. "Mon,Tue,Wed,Thu,Fri,Sat,Sun") — preferred over the numeric operatingDays bitmask column, which was not selected into the unified schema.
  • Example: Mon,Tue,Wed,Thu,Fri,Sat,Sun

detail_start_time / detail_start_time_range_max

  • Type: string (HH:MM:SS)
  • Description: Departure Time; _range_max is a companion "latest possible start" for products with a flexible start window (multi-stop pickups, flexible self-drive rentals, entry tickets valid across a window).
  • How built: Direct renames of raw fields timeStart (163/167 rows, 97.6%) and timeStartRangeMax (only 42/167 rows, 25.1% — kept per the same relevance check that kept product_duration_range_max).
  • Example (product 72): detail_start_time = "05:45:00", detail_start_time_range_max = "07:30:00" (earliest-to-latest pickup window across multiple Gold Coast/Brisbane pickup points).

Meta Fields

meta_supplier_id

  • Type: string (numeric-looking)
  • Description: Supplier account ID.
  • How built: Direct rename of raw field supplier.id.
  • Example: 2

meta_supplier_name

  • Type: string
  • Description: Supplier company name.
  • How built: Direct rename of raw field supplier.name.
  • Example: Australian Sunset Safaris

meta_supplier_website

  • Type: string (URL)
  • Description: Supplier website — per CLAUDE.md's unified schema table, Livn is the only source with this field.
  • How built: Direct rename of raw field supplier.website.
  • Example: https://www.sunsetsafaris.com.au/

meta_supplier_email

  • Type: string
  • Description: Supplier email — Livn-only field.
  • How built: Direct rename of raw field supplier.email. (Note: raw supplier.emailRes is identical to supplier.email in every row observed in Stage 1 and was excluded as redundant — not carried into Stage 2.)
  • Example: info@sunsetsafaris.com.au

meta_supplier_phone

  • Type: string
  • Description: Supplier phone — Livn-only field.
  • How built: Direct rename of raw field supplier.phoneRes. 142/167 rows (85.0%) populated.
  • Example: +617 3287 1644

Fields Livn Does NOT Populate

Per the unified schema table in CLAUDE.md, Livn is documented as a source for location_postcode (Rezdy, FH, Livn, Ingresso) and detail_max_age (Fareharbor only — Livn is not actually claimed there, no discrepancy). location_postcode is a real gap: raw locationsStart[0] objects observed in the data do carry a postcode key (visible in the raw location_source JSON, e.g. "postcode": "4217" for product 72), and supplier.postcode is also available (94.0% filled in Stage 1) — but neither was added to Stage 2's LOCATION_SCALAR_COLS extraction list or COLUMN_RENAME, so location_postcode is not present in unified_products.csv for Livn despite the raw source data existing to populate it. This is a gap between the schema-design doc and the actual Stage 2 build, worth flagging to whoever owns the unified schema — not something to silently work around in this reference doc.

Also worth noting: detail_max_age and detail_tripadvisor_rating/ detail_google_rating/detail_accessibility/detail_health_safety/ detail_languages/detail_cancellation_policy are documented in CLAUDE.md's Source Field Mapping table as null for Livn already (i.e. Livn genuinely has no source field for these) — those are expected absences, not gaps.

Fields Documented But Not Selected for the Unified Schema

These raw/Stage-1 columns exist in livn_stage1.csv but were deliberately excluded from livn_stage2.csv, so they never reach unified_products.csv. Listed here so a reader who finds them in an earlier pipeline stage doesn't wonder where they went:

  • All TDU-account-level and channel/distributor/catalogue metadata (distributor.*, channel.*, catalogue.*, currencies, usesNetRates, commissionPerc) — 100% constant across all 167 rows, describes TDU's own Livn account, not per-product data.
  • disabled, supplier.disabled, supplier.demo, demo — 100% False internal flags, no variation.
  • catalogueProductId, supplier.catalogueSupplierId — internal Livn catalogue IDs, redundant with id/supplier.id.
  • supplier.nameCompany, supplier.nameTradingAs — largely duplicate supplier.name.
  • supplier.description, supplier.logo.* (5 columns), supplier.address1, supplier.address2 — supplier-level (not per-product) company/branding/office data, no unified schema slot.
  • supplier.emailRes — identical to supplier.email in every row, redundant.
  • supplier.v1Cid, supplier.created, supplier.resSystem, supplier.businessNumber (except as folded into detail_booking_notes as "ABN: ..."), v1Cid, created, resSystem — internal tracking/legacy-system fields, not customer-facing.
  • _filename_product_id, _source_filename — ETL's own bookkeeping columns.
  • operatingDays — numeric bitmask duplicate of operatingDaysStr, which was selected instead.
  • supplier.city, supplier.state / supplier.state_clean, supplier.postcode, supplier.country — supplier-level location fallbacks flagged as possibly useful in the Stage 2 selection report, but Stage 2's actual build_livn_stage2.py uses only locationsStart[0] for all location_* scalar fields — these supplier-level columns were not wired in as a fallback.
  • supplier.tnc / supplier.tnc_clean — supplier terms & conditions text; flagged in the Stage 2 selection report as possibly supporting a cancellation-policy field, but no unified detail_cancellation_policy mapping exists for Livn (confirmed null in CLAUDE.md's Source Field Mapping table) and it was not carried into Stage 2.
  • operatingSchedule — human-readable schedule description (73.1% empty), left out in favor of the higher-fill-rate operatingDaysStr.
