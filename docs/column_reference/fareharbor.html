Fareharbor — Unified Schema Field Reference

Scope: Every unified-schema column that Fareharbor actually populates in data_pipeline/unified_database/unified_products.csv (source = "Fareharbor"). Fareharbor supplies 37 of the 87 unified columns; the rest are always blank for this source and are not documented here.

Audience: Team members looking up what a field means and where it comes from. This is NOT a data-quality report — for null rates, outliers, and QA flags see the HTML data-quality dashboard instead.

Pipeline stages behind this doc (oldest → newest): 1. parsers/fareharbor_etl.py — reads data/Fareharbor/*.json (root key item), writes the 41-column V1 ETL base. 2. scripts/build_fareharbor_etl_v2.py — adds regex/HTML heading-extraction columns (not selected into the unified schema — see Note below). 3. scripts/step21_build_final_merge.py — merges in AI-extracted desc_about_*/booking_notes_* "sandwich" columns from 11 OpenAI Batch API output files, writing exports/fareharbor_final.csv. 4. scripts/build_fareharbor_stage2.py — renames/selects columns to unified names and performs 3 real field merges, writing data_pipeline/stage2/fareharbor_stage2.csv. 5. scripts/build_unified_database.py — folds Stage 2 into unified_products.csv; for Fareharbor this only normalizes product_currency (uppercase) and derives product_price_numeric — no renaming, no further merging.

Note on the AI-extraction pipeline: several detail_* fields below are populated by an LLM extraction pass (the "V2 sandwich" pipeline, see config/fareharbor_prompts.txt and the changelog at reports/fareharbor_pipeline_changelog.html), not read directly off the raw Fareharbor API. Where that's the case, it's called out explicitly.

Example product used throughout: product_id = 328397 ("Trail Blazer Safari", supplier alias 4trackadventure) — chosen because it has real, non-empty values in every merged field, so the merge behavior is visible.

Identity

product_id

  • Type: string (numeric-looking, e.g. "328397")
  • Description: Fareharbor's unique product identifier.
  • How built: Direct from raw JSON item["pk"] — NOT the filename. (parsers/fareharbor_etl.py)
  • Example: 328397

source

  • Type: string (constant)
  • Description: Marks which of the 6 supplier systems this row came from.
  • How built: Hardcoded literal "Fareharbor" (normalized from the raw API's "FareHarbor" capitalization per CLAUDE.md Critical Rule #1).
  • Example: Fareharbor

supplier_alias

  • Type: string
  • Description: Human-readable operator/company slug.
  • How built: Parsed from the source filename (Fareharbor-{supplierAlias}-{productId}.json) via get_supplier_alias(), which joins all middle hyphen-segments back together — this correctly handles aliases that themselves contain hyphens (e.g. 42southsurfschool-surfgroms).
  • Example: 4trackadventure

Listing Page Fields

product_name

  • Type: string
  • Description: Full tour/product name.
  • How built: Direct from raw field item.name.
  • Example: Trail Blazer Safari

product_headline

  • Type: string
  • Description: Short tagline shown under the product name.
  • How built: Direct from raw field item.headline.
  • Example: Ages 14+ – 1 Hour – Awesome Scenery – Highly Recommended (raw source text uses •/en-dash-style separators; some values contain mojibake from upstream encoding issues — see CLAUDE.md's ftfy note.)

product_price

  • Type: number (string-formatted decimal, dollars)
  • Description: Starting price for the product.
  • How built: Raw field customer_prototypes[0].total, stored in cents in the source API, divided by 100 in get_price_info().
  • Example: 173.04

product_price_numeric

  • Type: number
  • Description: Companion numeric-price column added at the unified-database merge step so every source has one consistent numeric price field (needed because Livn's product_price is a JSON object, not a scalar).
  • How built: For Fareharbor, product_price is already a scalar, so this is just float(product_price) cast straight through — no transformation. (build_unified_database.py::derive_price_numeric())
  • Example: 173.04

price_including_tax

  • Type: number (decimal, dollars)
  • Description: Tax-inclusive version of the starting price — not a named unified schema field itself, but kept as a useful companion to product_price for the pricing display.
  • How built: Raw field customer_prototypes[0].total_including_tax, divided by 100.
  • Example: 199.0

product_currency

  • Type: string (ISO code)
  • Description: Currency the price is quoted in.
  • How built: Not a real API field — Fareharbor's raw API has no explicit currency field. Inferred purely from tax_percentage: 10% → AUD, 15% → NZD, anything else defaults to AUD. Uppercased at the unified-database merge step.
  • Example: NZD

price_options_summary

  • Type: string
  • Description: Human-readable breakdown of all fare tiers and their prices — supports product_price.
  • How built: Computed by joining every entry in raw customer_prototypes as "{display_name}: ${price}".
  • Example: Person: $173.04

prototype_count

  • Type: integer
  • Description: Number of distinct fare tiers/pricing options for the product — supports price_options_summary.
  • How built: Computed as len(item.customer_prototypes).
  • Example: 1

product_duration / duration_text

  • Type: product_duration = number (minutes); duration_text = string (human-readable)
  • Description: How long the tour runs.
  • How built: Both come from raw field item.structured_description.duration. duration_text is the raw string as written by the supplier; product_duration is a numeric-minutes parse of that same string via parse_duration_minutes() — it will legitimately be blank even when duration_text isn't, if the text couldn't be parsed into a number (e.g. free-text like "Full day").
  • Example (this product): both blank — structured_description.duration was empty for this listing; itinerary text ("Allow 1 Hour") carries the real duration instead. A populated example elsewhere in the dataset: duration_text = "2 Hours", product_duration = 120.

product_images / product_main_image / image_count

  • Type: product_images = JSON-list of URL strings; product_main_image = single URL string; image_count = integer
  • Description: Gallery images and the single cover image (Fareharbor is the only source with a distinct main-image field — per the unified schema table).
  • How built: product_images from raw item.images[].image_cdn_url, collected into a JSON array. product_main_image direct from raw item.image_cdn_url. image_count computed as len(image_urls).
  • Example: product_main_image = "https://cdn.filestackcontent.com/qaakaAZQFGw8I1AfO5QY", image_count = 7

product_tags

  • Type: string (pipe-joined list)
  • Description: Keyword tags for the product.
  • How built: Raw item.tags[].name, joined with " | ".
  • Example: Guided Tour

Location Fields (Details API only, per Critical Rule #8)

location_street, location_city, location_state, location_country, location_postcode

  • Type: string
  • Description: Structured street address components.
  • How built: Direct from raw item.locations[0].address.{street,city,province,country,postal_code} (falls back to item.primary_location where locations is absent). location_country is uppercased at the unified-database merge step, and mapped from a small set of known full-country-names to ISO-2 codes (e.g. "Australia" → AU) — anything already 2 letters, or not in that mapping, passes through unchanged.
  • Example: location_street = "320 Wilson Road, South Head", location_city = "Auckland", location_state = "Auckland", location_country = "NZ", location_postcode = "0874"

location_latitude / location_longitude

  • Type: number
  • Description: GPS coordinates.
  • How built: Direct from raw item.locations[0].latitude / .longitude.
  • Example: -36.584088, 174.293667

Detail Page Fields

detail_description

  • Type: string (long text)
  • Description: "About the Experience" section.
  • How built: Already a merged field at the V1 ETL stage: prefers item.structured_description.description, falls back to raw item.description only when the structured field is empty. Passed straight through to the unified name at Stage 2 (no further merge).
  • Example: "For the Most fun you will ever have on 4 Wheels, Ride through beautiful Forest Tracks while looking at amazing Coastal scenery\n1 Hour\nNo experience needed..."

detail_highlights

  • Type: string (long text)
  • Description: "Tour Highlights" section.
  • How built: Not what the field name might suggest (structured field with AI fallback) — the Stage 2 build script uses only the AI-extracted value: raw column desc_about_highlights, produced by the LLM "sandwich" extraction pass over detail_description/booking notes (step21_build_final_merge.py → scripts/build_fareharbor_stage2.py COLUMN_RENAME). The separately-available structured field (item.structured_description.highlights, ETL column desc_highlights) exists in Stage 1 but was not selected for this unified column.
  • Example: "Ride through beautiful Forest Tracks while looking at amazing Coastal scenery.\nThis tour Rides through Manuka and Kanuka forrest tracks..."

detail_itinerary

  • Type: string (long text)
  • Description: Cruise Route / Itinerary section.
  • How built: Same pattern as detail_highlights — Stage 2 uses only the AI-extracted desc_about_itinerary column. The structured item.structured_description.itinerary field is not used here.
  • Example: "Tour starts at 8.30 am or 3.30 pm.\nAllow 1 Hour."

detail_what_is_not_included

  • Type: string (long text)
  • Description: What's Not Included section (Fareharbor-only field per the unified schema).
  • How built: Same pattern — Stage 2 uses only the AI-extracted desc_about_what_excluded column, not the structured structured_description.what_is_not_included field.
  • Example: "No drinking of alcohol before going on a safari will be tolerated and you will be banned if you are considered unfit to ride, without a refund of your money."

detail_what_to_bring

  • Type: string (long text, pipe-joined when two sources both have content)
  • Description: What To Bring section.
  • How built: A genuine 2-source merge (build_fareharbor_stage2.py MERGE1_SRC): desc_about_what_to_bring (AI-extracted from the description/highlights text) and booking_notes_what_to_bring (AI-extracted from booking-notes text — a separate extraction pass over different source text). If both are non-empty, they're joined with " | "; if only one is present, that one is used as-is.
  • Example: "Bring sturdy shoes, long pants and your camera.\nBring your camera and a secure bum bag or small backpack..." (single source populated in this example.)
  • Merge stats (11,231 rows total): both sources populated → 1,842 rows (joined with |); desc_about_what_to_bring only → 991; booking_notes_what_to_bring only → 2,960; neither → 5,438.

detail_what_is_included

  • Type: string (long text, pipe-joined when two sources both have content)
  • Description: What's Included section.
  • How built: A genuine 2-source merge, same join rule as detail_what_to_bring: desc_about_what_included (AI-extracted) + booking_notes_inclusions. Note: booking_notes_inclusions is misleadingly named — despite the booking_notes_* prefix, its actual extracted content is "items/services included at no extra cost" (verified against config/fareharbor_prompts.txt's field definition and real samples), which is why it was routed into detail_what_is_included rather than detail_booking_notes.
  • Example: "We supply, helmets, goggles and wet weather gear.\nWe provide a lock up container that you can leave personal items in.\nWe provide FREE photos on the tour. | We supply all safety gear I.e. helmets and..." — this example shows both sources populated (the | join is visible mid-string).
  • Merge stats (11,231 rows total): both sources populated → 1,654 rows; desc_about_what_included only → 4,836; booking_notes_inclusions only → 787; neither → 3,954.

detail_booking_notes

  • Type: string (long text, pipe-joined concatenation of up to 6 sources)
  • Description: Important Information section.
  • How built: A 6-way concat (build_fareharbor_stage2.py MERGE2_SRC), not a 2-way primary/fallback pair: desc_booking_notes (itself already a merge of structured_description.check_in_details falling back to raw item.booking_notes) + AI-extracted booking_notes_location, booking_notes_check_in, booking_notes_important_info, booking_notes_cancellation, booking_notes_itinerary. Every non-empty source is joined with " | " in that fixed order; empty ones are simply skipped (not represented by an empty segment). Two AI-extracted columns from the same sandwich pass, booking_notes_departure_info and booking_notes_other, are deliberately excluded from this merge (kept out at both the original fareharbor_final.csv stage and Stage 2).
  • Example: "DIRECTIONS TO OUR BASE: We have no signage currently, so please follow Instructions. Head down Wilson Road (Gravel Road) there are 2 White fridges on the right hand side of the road. Go to the second..."
  • Merge stats (11,231 rows total, count of the 6 sources populated per row): 0 of 6 → 2,189 rows; 1 of 6 → 3,741; 2 of 6 → 1,973; 3 of 6 → 1,635; 4 of 6 → 1,182; 5 of 6 → 460; 6 of 6 → 51. Average combined length 656.8 characters, max 11,328 characters.

detail_cancellation_policy

  • Type: string (long text)
  • Description: Cancellation Policy section.
  • How built: Raw field item.cancellation_policy, HTML-stripped. Despite the naming (cancellation_policy vs. ETL column desc_cancellation) looking like a raw/parsed pair, it is not — desc_cancellation = strip_html(cancellation_policy) in parsers/fareharbor_etl.py line 235, i.e. the exact same source value, just cleaned. Confirmed by identical fill rates (98.3%/98.3%, same 11,044 rows) in reports/fareharbor_stage2_column_selection.md. Stage 2 selects the cleaned (desc_cancellation) version under the unified name.
  • Example: "CANCELLATIONS: Any deposits are non refundable\nIf you cancel or alter your booking:\n- Within 14 days of the booked date - loss of full payment..."

cancellation_type / cancellation_hours

  • Type: cancellation_type = string; cancellation_hours = number
  • Description: Structured, machine-readable companions to detail_cancellation_policy — not named unified-schema fields themselves, but kept for portal logic that needs a cutoff without parsing free text.
  • How built: Direct from raw item.effective_cancellation_policy.type and .cutoff_hours_before.
  • Example: cancellation_type = "hours-before-start", cancellation_hours = 24.0

detail_tax_percentage

  • Type: number
  • Description: Tax percentage applied (Fareharbor-only field per the unified schema).
  • How built: Direct from raw item.tax_percentage. (Also the field this source's product_currency inference is derived from — see above.)
  • Example: 15

detail_health_safety

  • Type: string (long text)
  • Description: Health & Safety section.
  • How built: Direct from raw item.health_and_safety_policy.
  • Example: blank for this product (92.6% null rate for this field across Fareharbor overall).

is_pickup_available

  • Type: boolean
  • Description: Whether pickup is ever offered for this product — not a named unified field, kept as useful real metadata for booking-flow/location display.
  • How built: Direct from raw item.is_pickup_ever_available.
  • Example: False

Fields Fareharbor Does NOT Populate

Per the unified schema table in CLAUDE.md, Fareharbor is documented as the source for detail_accessibility, detail_min_age, detail_max_age, detail_group_size, detail_tripadvisor_rating, detail_google_rating — these came from item.structured_description.{accessibility,min_age,max_age, group_size} and rating fields at the raw-API level, but none of them made it into fareharbor_stage2.csv's COLUMN_RENAME list, so they are not present in unified_products.csv for this source despite being documented as available. This is a gap between the schema-design doc and the actual Stage 2 build — worth flagging to whoever owns the unified schema, not something to silently work around in this reference doc.

Fields Documented But Not Selected for the Unified Schema

These raw/Stage-1 columns exist in fareharbor_final.csv but were deliberately excluded from fareharbor_stage2.csv, so they never reach unified_products.csv. Listed here so a reader who finds them in an earlier pipeline stage doesn't wonder where they went:

  • All parsed_txt_* / parsed_html_* columns (22 columns) — an independent, lower-coverage regex/heading-extraction attempt from build_fareharbor_etl_v2.py, superseded by the AI extraction pass.
  • desc_extraction_method, has_structured_desc, txt_sections_found, html_sections_found, txt_sections_count, html_sections_count, needs_chatgpt, empty_sections_count, empty_sections_list — internal pipeline/QA metadata, not customer-facing.
  • desc_about_duration_text, desc_about_other, booking_notes_departure_info, booking_notes_other — AI-extracted sandwich columns with no corresponding unified field or Figma section.
  • desc_highlights, desc_what_included, desc_itinerary, desc_what_excluded — the structured (non-AI) counterparts that lost out to the AI-extracted versions for detail_highlights/detail_what_is_included/detail_itinerary/detail_what_is_not_included (see those fields' "How built" notes above).
  • booking_notes (raw, unmerged) and desc_booking_notes (the earlier ETL-stage partial merge) — superseded by the full 6-way detail_booking_notes merge at Stage 2.
  • desc_cancellation — same underlying value as cancellation_policy/detail_cancellation_policy, not a second source (see that field's note above).
  • compound_key — regenerable (product_id|source), not carried into Stage 2.
